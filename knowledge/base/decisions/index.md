> Architecture decision records (ADR).

# Architecture decisions

* [ADR-0001: Adopt Google's Open Knowledge Format as the basis of the standard](ADR-0001-adopt-google-okf.md) - Project knowledge is represented as an OKF bundle (markdown + YAML frontmatter) instead of a format of our own.
* [ADR-0002: One bundle per repository in knowledge/](ADR-0002-knowledge-folder-per-repo.md) - Each repo carries its knowledge in knowledge/, co-located with the code, not in a central repo.
* [ADR-0003: Profile directories and types in Spanish](ADR-0003-spanish-names.md) - Profile directories and type values are in Spanish, except references/ and Attested Computation, which the spec fixes. _(deprecated)_
* [ADR-0004: Support OKF v0.1 and v0.2, with v0.2 as the default](ADR-0004-dual-support-v01-v02.md) - The profile writes v0.2, reads and validates v0.1, and migrates in both directions without mixing forms in a bundle.
* [ADR-0005: generated required and verified only by people](ADR-0005-required-generated-human-verified.md) - The profile requires generated on every concept and forbids an agent from writing verified with a human: actor. _(deprecated)_
* [ADR-0006: Python scripts without external dependencies](ADR-0006-dependency-free-scripts.md) - The tools (init, lint, index, migrate) are Python ≥ 3.9 without pip; PyYAML is used only if present. _(deprecated)_
* [ADR-0007: Single source of skills and per-platform projections](ADR-0007-single-source-and-projections.md) - Skills live only once in plugin/okf-builder/skills; each platform receives a projection (symlink or generated package).
* [ADR-0008: The okf-builder repo documents its own knowledge with OKF](ADR-0008-dogfooding.md) - This repository applies profile knowledge/1.0 to itself; the project's decisions are ADRs in knowledge/decisions.
* [ADR-0009: Build multi-stage changes in layers and delegated tickets](ADR-0009-build-in-layers-and-tickets.md) - Changes that touch several layers of the repo are split into verifiable tickets that agents build in isolated worktrees, and the main session only judges, verifies and merges.
* [ADR-0010: English as the repo's canonical language and profile knowledge/2.0](ADR-0010-english-canonical-profile-2.md) - The profile vocabulary, the code, the skills and the repo's knowledge move to English, with a fixed glossary; the vocabulary change bumps the profile to knowledge/2.0.
* [ADR-0011: Scripts run with uv and declare PyYAML inline (PEP 723)](ADR-0011-uv-pep723-scripts.md) - The okf-standard scripts declare PyYAML in PEP 723 inline metadata and run with uv run, the reduced YAML parser is removed, and each script carries its own tests.
* [ADR-0012: Knowledge fragments are captured as they happened and distilled into the bundle](ADR-0012-knowledge-fragments-and-distillation.md) - A meeting, discussion or transcript is stored as an immutable Fragment concept, and a distillation step proposes the additions, updates and conflicts it brings to the bundle for a person to resolve. _(deprecated)_
* [ADR-0013: One knowledge-architect agent for Claude and Microsoft 365 Copilot](ADR-0013-agent-projections.md) - The knowledge-architect agent is written once as a Claude plugin agent and generated into a Microsoft 365 Copilot declarative agent; other platforms keep using the skills until there is a need for their agent formats. _(deprecated)_
* [ADR-0014: A knowledge repository has one source, Git or SharePoint; other tools read it](ADR-0014-knowledge-repository-storage.md) - A team's knowledge bundle has exactly one editable copy, a Git repository by default or a SharePoint library for teams without Git; Microsoft 365, Google Drive and Obsidian read it, and the bundle starts as one monorepo with a stated rule for splitting by domain.
* [ADR-0015: Knowledge fragments follow the KDD bundle's format, and conflicts go to one register](ADR-0015-fragment-format-and-conflict-log.md) - A fragment is a Knowledge Fragment with occurred_at, origin, participants and distillation_status; each bundle keeps one Conflict Log; okf-fragment, okf-distill and okf-review are separate skills, and distillation still needs a person's approval. _(deprecated)_
* [ADR-0016: Distillation adds refutation: an outdated concept is deprecated without opening a conflict](ADR-0016-refutation-as-a-distillation-kind.md) - Fragments keep the KDD format and one Conflict Log per bundle; distillation classifies each item as an addition, confirmation, update, refutation or conflict, where a refutation proposes deprecating a concept and naming its replacement, and only disputed items open a conflict. _(deprecated)_
* [ADR-0017: The Claude agent preloads every skill it needs; the Microsoft 365 agent takes a configured subset](ADR-0017-agent-skills-per-platform.md) - The knowledge-architect agent is still written once as a Claude plugin agent and generated into a Microsoft 365 Copilot declarative agent, but only M365's caps bind M365; the Claude agent lists every skill the role uses, and tools/m365-agent.json picks the at most 8 skills the M365 agent carries.
* [ADR-0018: A bundle has three layers, fragments, base and projections, in profile knowledge/3.0](ADR-0018-three-layers-fragments-base-projections.md) - The bundle separates what was said (fragments/), what is known (base/, holding the typed directories) and what is derived for a reader (projections/); moving the typed directories under base/ is a breaking change, so the profile becomes knowledge/3.0 with a migration from 2.0. _(deprecated)_
* [ADR-0019: Knowledge projections derive from the base for a reader, declared in a projection.yaml and checked for drift by content hash](ADR-0019-knowledge-projections.md) - A projection is a directory in knowledge/projections/ with a projection.yaml (lifecycle, nature, intent, refs with their hashes), its content and its rendered deliverables; it is not OKF and has its own tools, it never regenerates by itself, and this repository's per-platform outputs of the skills are renamed platform packages. _(deprecated)_
* [ADR-0020: A domain declares its own taxonomy in a Domain Profile concept, which lint and the skills read](ADR-0020-domain-profiles.md) - A directory under base/ may hold a profile.md of type Domain Profile that declares the domain's types (each extending a profile type), their typed fields, the questions the domain answers, its dependencies and aliases for local names; it applies to its directory and below, and the tools read it instead of a fixed list. _(deprecated)_
* [ADR-0021: A bundle has three layers in profile knowledge/3.0; open questions are concepts in base/ and action items live in the team's tracker](ADR-0021-three-layers-with-open-questions.md) - The bundle separates what was said (fragments/), what is known (base/, holding the typed directories) and what is derived for a reader (projections/), in profile knowledge/3.0; an open question is an Open Question concept in base/ with an owner, and an action item lives in the team's tracker, never copied into the base.
* [ADR-0022: Knowledge projections are declared in a projection.yaml, and their drift is checked according to their nature](ADR-0022-knowledge-projections-drift-by-nature.md) - A projection is a directory in knowledge/projections/ with a projection.yaml (lifecycle, nature, intent, refs, versions), its content and its rendered deliverables; it is not OKF; a rendered projection is checked by regenerating it and comparing, a composed one by the content hashes of its refs, and a recomputable one by running its procedure again; nothing regenerates by itself.
* [ADR-0023: A bundle declares its taxonomy in one Domain Profile, with families per directory, composition rules and profiles shared by reference](ADR-0023-domain-profile-per-bundle.md) - A bundle's base/profile.md of type Domain Profile declares its types, typed fields, families (a schema per directory), questions and optional aliases, extends shared profiles by reference and never copies them, and follows written composition rules (an extension only adds, a duplicate id is an error, forbidden, fixed, by_type, named rules, validator delegation); lint and the skills read it. _(deprecated)_
* [ADR-0024: A fragment's record is immutable, and a missing capture field may be backfilled once from the record itself](ADR-0024-fragment-capture-field-backfill.md) - Fragments keep the KDD format, one Conflict Log per bundle and five kinds of distillation item; after capture the record never changes, but a missing occurred_at, origin or participants may be filled once, with a value read from the record or from an original its sources cite, approved by a person and logged.
* [ADR-0025: generated is required, and an agent writes a person's verification only from that person's recorded answer to a question naming each concept and version](ADR-0025-verification-recorded-by-question.md) - Every concept carries generated and starts as a draft; verified with a human actor is written by the person, or by an agent after that person answers a structured question naming each concept and its version, kept verbatim as a fragment and linked from the log. _(deprecated)_
* [ADR-0026: The standard's own types are a built-in Domain Profile, the first layer under each bundle's profile, with a level per requirement and typed actors and timestamps](ADR-0026-built-in-domain-profile.md) - A bundle's base/profile.md declares its taxonomy as in ADR-0023, on top of a built-in Domain Profile shipped with okf-standard that declares the standard's types; requirements carry a level (error or warn), field types add actor, datetime and date_or_datetime, checks across concepts stay in code, and lint reads references locally, runs validators only on request, resolves aliases and warns on undeclared keys only in bundles with a profile.
* [ADR-0027: The owner of an operational concept is a string; Actor stays as the OKF spec defines it](ADR-0027-owner-is-a-string-actor-stays-the-spec.md) - On API, Metric, Playbook, Policy, Runbook, System and Table, owner is a string that names a team or a person, so team:<team> is valid; an Open Question's owner stays an actor, and the actor convention stays exactly the spec's, with no team prefix.
* [ADR-0028: Where things go: four homes, workspace tooling as a projection of knowledge, and a Doctrine for how we build](ADR-0028-where-things-go.md) - The repo's files belong to one of four homes (product, product build, knowledge, workspace); the product is the only source of the standard and the templates, and their root copies are generated; the knowledge bundle carries no executable code except a Domain Profile's validators; workspace tooling such as an agent workflow is a projection of a knowledge concept and names it; how the repo builds with agents becomes a Doctrine, a local type refined as practice teaches.
* [ADR-0029: A fragment records its frozen material by SHA-256 and may freeze a repository at a commit, through a map field type](ADR-0029-fragment-material-and-repository.md) - A Knowledge Fragment may list the files its record was taken from, each with its SHA-256, and the repository it was taken from at a full commit; the standard gains a one-level map field type to declare both, lint hashes material found in the bundle and reports a changed file as an error, and okf-fragment adds the meeting discipline.
* [ADR-0030: The projection tools are a script and a skill, run a render only on request, and list recomputable projections for a person](ADR-0030-projection-tools.md) - okf_projection.py checks projection.yaml, the dependency rule and drift by nature, and the okf-projection skill creates, refreshes and renders projections; okf_lint stays OKF-only; a rendered projection's render command runs only on an explicit flag; a recomputable projection is listed for a person to recompute; the skill ships in the M365 packages but not in the M365 agent. _(deprecated)_
* [ADR-0031: The projection tools are a script and a skill, run a render only on request, never ask a transient projection to be committed, and list recomputable projections for a person](ADR-0031-projection-tools-transient-exception.md) - okf_projection.py checks projection.yaml, the dependency rule and drift by nature, and the okf-projection skill creates, refreshes and renders projections; okf_lint stays OKF-only; a rendered projection's render command runs only on an explicit flag, and what it writes is compared file by file, a transient projection's files never required to be committed; a recomputable projection is listed for a person to recompute; the skill ships in the M365 packages but not in the M365 agent.
* [ADR-0032: A bundle opens as an Obsidian vault through a viewer setup that a script writes, not a projection](ADR-0032-obsidian-viewer-setup.md) - okf_obsidian.py writes .obsidian/app.json, with Markdown links kept relative and updated on rename, and knowledge.base, with five Bases views over base/ and fragments/, at a bundle's root without overwriting; it is workspace configuration for one tool, neither a knowledge projection nor a platform package; okf-init offers it, make obsidian runs it here, and this repository commits both files.
* [ADR-0033: An agent writes a person's verification only from that person's recorded answer, given in a structured question or on a review page private to them, naming each concept and version](ADR-0033-verification-recorded-by-question-or-review-page.md) - Every concept carries generated and starts as a draft; verified with a human actor is written by the person, or by an agent from that person's recorded answer, given in the agent platform's question tool or on a review page private to the person that stores each answer with the concept's version, kept verbatim as a fragment and linked from the log.
* [ADR-0034: An organization receives okf-builder as its own package, copied in by a reviewed pull request per release, and each of its repositories pins the version that checks it](ADR-0034-organization-package.md) - A new generated platform package, the organization package, writes okf-builder's skills, its scripts as an installable package and the organization's Domain Profile into a bundle of the organization's own marketplace through a reviewed pull request per release; each repository of the organization records the version in its root index and runs lint at that version from that marketplace, never from a copy; other OKF dialects the organization runs converge on this standard as Domain Profiles and validators. _(deprecated)_
* [ADR-0035: The product build runs with just, and its checks are named steps of a build script](ADR-0035-just-build-runner.md) - A justfile replaces the Makefile as the product build's runner; every check of just test is a named step of build/checks.py, a PEP 723 script that runs the scripts as a person would and writes to one temporary directory per run; the root copies are written by build/copies.py; earlier ADRs keep naming make as the history of the decisions they record.
* [ADR-0036: Releases are proposed by release-please from squash-merged pull requests with Conventional Commit titles, and a workflow attaches the platform packages](ADR-0036-release-please.md) - The plugin's version rises only when the plugin changes, and the marketplace manifest keeps its own version, raised by hand when the manifest changes; one plugin version covers every package okf-builder ships; a change is breaking when a bundle that passed lint fails it; pull requests are squash-merged and their titles follow Conventional Commits, so each change reaches main as one commit release-please reads; release-please keeps a release pull request open that bumps the version in plugin.json and marketplace.json and writes CHANGELOG.md; merging it tags and publishes the release, and a GitHub Actions workflow builds the platform packages with just all and attaches them; a CI workflow runs just test and just lint on every pull request and checks its title; knowledge/log.md keeps the knowledge history and records each release in one line.
* [ADR-0037: An organization receives a copy of okf-builder that it owns and versions, pulls later releases when it chooses, and runs lint from the installed plugin](ADR-0037-organization-distributed-copy.md) - The organization package, generated from a tagged release of okf-builder, delivers the skills with their scripts as plain files, the organization's Domain Profile and a pre-commit hook; once delivered the copy is the organization's, which may take it in its own direction and versions it by its own release process while recording the okf-builder version it was taken from; a later okf-builder release reaches it only when the organization pulls it, by a pull request in its own repository; its repositories run lint from the plugin each person installs, with no pinned version; the installable scripts package is deferred; other OKF dialects still converge as Domain Profiles and validators. Supersedes ADR-0034.
* [ADR-0038: A domain bundle defines its operational kinds in base and holds their instances as bundles next to its layers, each naming its parent](ADR-0038-domain-and-operational-bundles.md) - A bundle is either a domain bundle, whose knowledge never closes, or an operational bundle, a unit of work that opens and closes; the domain bundle's Domain Profile defines each operational kind (its directory, its states and the kinds it may hold) and a family of base/ says how that work is done; each instance is a full bundle stored in its kind's directory next to the layers, never inside base/, whose root index.md declares kind, state, parent and a declarative depends_on; lint recurses into instances; a closing instance distills its whole base/ one level up, each concept promoted, opened as a conflict or kept, and closes only once its open conflicts and questions are resolved or carried up; a closed one is frozen or extracted. _(deprecated)_
* [ADR-0039: A domain bundle defines its operational kinds and holds their instances next to its layers; a closing instance distills into its parent, which keeps the closing fragment, through okf_close.py](ADR-0039-closing-operational-bundles.md) - A bundle is either a domain bundle, whose knowledge never closes, or an operational bundle, a unit of work that opens and closes; the domain bundle's Domain Profile defines each operational kind and each instance is a full bundle in its kind's directory next to the layers, whose root index.md declares kind, state, parent and a declarative depends_on; lint recurses into instances; a closing instance distills its whole base/ one level up through the script okf_close.py, the approved change set kept as a closing fragment in the parent, links running down only, and closes only once its open conflicts, open questions and pending fragments are resolved or carried up, marked carried; the audit reports a concept edited after closing; Microsoft 365 Copilot does not ship the closing; supersedes ADR-0038.
* [ADR-0040: A decision is a Decision; Architecture Decision is one kind of it, and each kind has its own folder, prefix and sequence](ADR-0040-decision-types.md) - The standard gains an abstract built-in type Decision that Architecture Decision extends, with no catalogue of kinds; each decision type declares its folder and prefix in the profile, has its own template and numbers on its own sequence; this repository declares a local Standard Decision, keeps plain Decision for how the repo works, and moves and renumbers the 30 decisions that are not about the plugin's architecture.
