# Decisions

* [DEC-0001: The okf-builder repo documents its own knowledge with OKF](DEC-0001-dogfooding.md) - This repository applies profile knowledge/1.0 to itself; the project's decisions are ADRs in knowledge/decisions.
* [DEC-0002: Build multi-stage changes in layers and delegated tickets](DEC-0002-build-in-layers-and-tickets.md) - Changes that touch several layers of the repo are split into verifiable tickets that agents build in isolated worktrees, and the main session only judges, verifies and merges.
* [DEC-0003: Where things go: four homes, workspace tooling as a projection of knowledge, and a Doctrine for how we build](DEC-0003-where-things-go.md) - The repo's files belong to one of four homes (product, product build, knowledge, workspace); the product is the only source of the standard and the templates, and their root copies are generated; the knowledge bundle carries no executable code except a Domain Profile's validators; workspace tooling such as an agent workflow is a projection of a knowledge concept and names it; how the repo builds with agents becomes a Doctrine, a local type refined as practice teaches.
* [DEC-0004: The product build runs with just, and its checks are named steps of a build script](DEC-0004-just-build-runner.md) - A justfile replaces the Makefile as the product build's runner; every check of just test is a named step of build/checks.py, a PEP 723 script that runs the scripts as a person would and writes to one temporary directory per run; the root copies are written by build/copies.py; earlier ADRs keep naming make as the history of the decisions they record.
* [DEC-0005: Releases are proposed by release-please from squash-merged pull requests with Conventional Commit titles, and a workflow attaches the platform packages](DEC-0005-release-please.md) - The plugin's version rises only when the plugin changes, and the marketplace manifest keeps its own version, raised by hand when the manifest changes; one plugin version covers every package okf-builder ships; a change is breaking when a bundle that passed lint fails it; pull requests are squash-merged and their titles follow Conventional Commits, so each change reaches main as one commit release-please reads; release-please keeps a release pull request open that bumps the version in plugin.json and marketplace.json and writes CHANGELOG.md; merging it tags and publishes the release, and a GitHub Actions workflow builds the platform packages with just all and attaches them; a CI workflow runs just test and just lint on every pull request and checks its title; knowledge/log.md keeps the knowledge history and records each release in one line.
