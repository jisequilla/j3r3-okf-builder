## How this repo handles those principles

The owner asked:

> so having this detail, how are we handling this principles and this detail?

The agent read the standard, the `okf-ask` skill and the lint script, ran lint on `knowledge/`, and answered that the repo covers four of the five principles and goes further than the video on trust, while attestation is covered in shape only:

- Provenance: `generated: { by, at }` is required on every concept, where the spec leaves it optional, with `sources[]`; fragments keep the event a concept was distilled from ([ADR-0012](/base/decisions/ADR-0012-knowledge-fragments-and-distillation.md)).
- Trust: the same three tiers as the video, derived from `verified` and never stored ([Trust level](/base/domain/trust-level.md)); an agent writes `verified` with a `human:` actor only from that person's recorded answer naming the concept and its version ([ADR-0033](/base/decisions/ADR-0033-verification-recorded-by-question-or-review-page.md)).
- Freshness: `stale_after` is recommended for runbooks, metrics and policies; lint warns once it has passed and `okf-ask` warns when it answers from a stale concept.
- Lifecycle: `draft` on creation, `stable` after review, `deprecated` never deleted and linked to its replacement.
- Attestation: the type `Attested Computation` exists and lint checks its shape (`runtime`, a single `# Computation` block, `okf_lint.py` lines 341 to 350). Nothing runs or verifies a computation.

On the video's demo, the agent said this repo handles two competing definitions earlier than the video does: `okf-distill` opens a conflict in the Conflict Log and a person resolves it by superseding or deprecating one side, with who decided and why recorded, where the video's fix is a hand edit of one `status` field. At read time `okf-ask` flags a deprecated concept and, when two concepts contradict, says so and prefers the most recent verified one.

## Is okf-ask an attester

The owner asked:

> ok so question inst okf-ask kind of an attesters?

The agent answered no, from the spec copy (`OKF-SPEC-v0.2.md` lines 104, 604 to 605 and 712). An attester is deterministic code with no LLM that takes a receipt, the evidence a run returns, and gives a verdict on whether a number was produced by the sanctioned computation. `okf-ask` is an LLM that reads concepts and reports the trust signals already written on them; it checks nothing against the world. In the spec's terms `okf-ask` is a consumer, and in the attestation flow the consumer is the party that runs the attester over the receipt.

The agent set the two side by side: the trust signals answer "can I believe this definition?", answered by a person and recorded in `verified`; attestation answers "was this number produced the sanctioned way?", answered by deterministic code over a receipt, which nothing in this repo runs. The nearest thing in spirit is `okf_lint.py`, deterministic and without an LLM, but it judges a bundle's form, not a computation's receipt.

## Where an Attested Computation applies

The owner said they did not want `okf-ask` to take part in attestation, and asked:

> no i don't what it to be part in attestation, but still we can build on it, since for example every new metadata we define in the frontmatter of each Domain Bundle and each domain concept serves to answer a question in the knowledge, so our attester computation could be how to calculate that aggregated knowledge for example or am i understanding it wrong? also since we yet to define and not in this repo since this repo has no data and is a meta repo plugin to define and automate how to hanlde okf on other projects, when a domain needs to calculate something it would need an attested computation, did i understand it right?

The agent answered that the second point is right and the first half right.

On the second: this repo is the meta layer, defining the type, the template and the lint shape check, with no data and so no computations of its own. A domain bundle is where they live: a `Metric` says what a number means and links to an `Attested Computation` that says how it is produced (spec §10.1). "Needs" is too strong: the spec makes it optional and the built-in profile describes the link without requiring it; it is for numbers that must be produced one sanctioned way. The domain supplies the executor and attester code, since the spec says OKF "does not execute anything itself" and nothing in the plugin runs them.

On the first: a field the Domain Profile declares can be mapped to a question (`questions`, `field: Type.field`), and today `okf-ask` answers it by reading frontmatter concept by concept, the script returning only the mapping. That is an improvised computation. But attestation solves another problem, an untrusted agent running a query on a remote system, with a receipt to prove afterwards that it ran the sanctioned one; an aggregation over the bundle is local, small and deterministic to read, so a script that computes it needs no receipt and no attester. The agent suggested, as what could be built instead, a script mode that returns each concept's value for the mapped field with the gap, for `okf-ask` to cite; it would be a change to skills and scripts and start with an ADR.

The owner closed the point:

> i just wnated to make sure we are covering this, when we need it, when a real attested computation is needed and i understanded the concept

The agent confirmed the owner's understanding and that the repo is covered for that day: the type in the built-in profile, the `computation.md` template, the directories `base/computations/` and `base/references/attesters/`, the lint checks, and Google's v0.2 sample as a fixture in `just test`. The computation, the executor instructions and the attester code are the domain's to bring. Nothing to build now; the first real domain bundle with a metric will test whether the template and the lint checks are enough.

## What the knowledge architect has when it distills

The owner asked:

> so one other question when the knowledge-architect runs in a project to process and distill the knowledge we capture in a fragment (this can came from a claude code chat, a meeting transcribe, a talke with some one or documents ) will the agent have the correct information to distribute the information and define the metric and ask the correct questions to what type of knowledge layer and domain distribution should be made?

The agent read the agent definition, `okf-distill`, `okf-capture` and the standard, and answered: mostly yes for routing and layers, with two gaps.

What the agent has: the routing table of `okf-distill` step 4, which sorts each item by what it is; the Domain Profile in force, read through `okf_lint.py --profiles` for each target directory; a path for knowledge that fits no type, a Domain Profile item of the change set that a person approves; fixed layers; and a ledger that accounts for every part of the record.

Where it is thin:

- Metrics. The only instruction is one line of `okf-capture` (`SKILL.md` line 22: "metric X is computed…" → Metric + Attested Computation if there is sanctioned SQL/code), which `okf-distill` reaches only through "apply with the `okf-capture` rules"; its own routing table never names a metric. Nothing tells the agent to ask who owns a metric, whether a sanctioned computation exists and when it goes stale.
- Which bundle. No step of `okf-fragment` or `okf-distill` asks whether a fragment belongs to the domain bundle or to an operational instance ([ADR-0038](/base/decisions/ADR-0038-domain-and-operational-bundles.md), [ADR-0039](/base/decisions/ADR-0039-closing-operational-bundles.md)); the bundle is the one found upwards from the working directory.
- Domain distribution is withheld from the agent on purpose: its definition says it does not define domains, the functional architect asks the business questions, and a person decides domains and bounded contexts.

The agent listed what the architect asks today: the owner of an open question the record does not name, the choice between a proposed ADR and an open question, and the approval of each change-set item. It does not ask clarifying business questions; those go back to the functional architect as gaps.

## No place and no answer

The owner said:

> is not about wanting, i want to understand if it make sense, now for what you tell me if something in the destillation does not have a place we will get an open question that the business/user/functional architect needs to get the ansswer so then this can be model correctly, and i think this is a good thing

The agent agreed it makes sense and corrected one point: "no place" and "no answer" are different cases.

- Nobody knows the answer: an `Open Question` in `base/questions/` with an owner, who gets the answer from the business; the concept is then written and the question marked answered.
- The knowledge is known and fits no type: a Domain Profile item in the change set (a local type, a field or a rule), settled by the person who approves the change set; the concept is written after it is approved.
- A claim with no source: left out of the bundle, or recorded as an `Open Question`.

In all three the agent does not guess, does not force the item into the wrong type and does not drop it silently. The cost the agent named: someone has to answer the open questions, and the standard's `review_on` date with its lint warning keeps the overdue ones visible. On the metric case, the agent said the mechanism works once the agent notices something is unknown; the weak spot is that nothing prompts it to notice a metric's missing owner or computation.

## The two beads

The owner asked for a bead for each gap:

> create a bead for the metric gap in okf-distill

> create a bead for the bundle-choice gap too

- `okf-kud`, feature, P3: `okf-distill` names no metric in its routing, so a metric's owner, computation and staleness go unasked. It asks for `okf-distill` to handle a metric explicitly, with what the record does not say becoming an open question or a change-set item. Out of scope: running executors or attesters.
- `okf-rn6`, feature, P3: `okf-fragment` and `okf-distill` never ask which bundle a fragment belongs to. It asks for an ADR on how a fragment's bundle is chosen, the capture step settling the destination from the record or by asking when open instances exist, and a rule for a fragment that concerns both a unit of work and the domain. Two checks come first, neither made in this session: how the upward search behaves from inside an instance directory, and whether `okf_close.py` already assumes fragments are captured inside the instance.

The agent chose P3 for both, since no bundle with metrics exists yet to meet the first.
