# j3r3-okf-builder

A project knowledge standard based on **OKF (Open Knowledge Format v0.2, Google)**, and a Claude Code / Cowork plugin that applies it in any repository.

## This repo uses OKF

The project's knowledge (decisions, architecture, runbooks, policies) lives in [`knowledge/`](knowledge/index.md). Every agent starts there; `AGENTS.md` (imported by `CLAUDE.md` and `GEMINI.md`) sets the rules.

## Single source and platform packages

The skills live once, in `plugin/okf-builder/skills/`. Each platform gets a platform package:

| Platform | Package | How |
|---|---|---|
| Claude Code | `.claude/skills` → symlink | on clone |
| GitHub Copilot, Gemini CLI | `.agents/skills` → symlink | on clone |
| Claude Cowork | `okf-builder.plugin` | `just plugin` |
| Microsoft 365 Copilot | `dist/m365/okf-builder-m365.zip` + `dist/m365/skills/*.zip` | `just m365` |
| Other repos | `dist/copilot/` (`.github/skills` + `@okf` agent) | `just copilot` |

`just all` regenerates the root copies and builds everything once `just test` passes. On Windows without `core.symlinks`, use `just copilot` and copy.

## Contents

Every file belongs to one of four homes ([ADR-0028](knowledge/base/decisions/DEC-0003-where-things-go.md)). The plugin is the only source of the standard and the templates: the root `standard/` and `templates/` are copies generated by `just copies`, and `just test` fails when they are stale. To change them, edit `plugin/okf-builder/skills/okf-standard/` and run `just copies`.

| Home | Path | What it is |
|---|---|---|
| Product | `plugin/okf-builder/` | Plugin / single source: the skills `okf-standard`, `okf-init`, `okf-capture`, `okf-fragment`, `okf-distill`, `okf-review`, `okf-lint`, `okf-index`, `okf-ask`, `okf-migrate`, `okf-projection` + Python scripts run with uv (PEP 723), the templates, the standard, and the `knowledge-architect` agent. |
| Product | `standard/OKF-STANDARD.md` | The standard: the `knowledge/3.0` profile (structure, frontmatter, types, lifecycle, conformance). Generated copy of `okf-standard/references/OKF-STANDARD.md`. |
| Product | `standard/OKF-COMPATIBILITY.md` | OKF v0.1 ↔ v0.2 differences, field matrix, mapping rules and versioning policy. Generated copy of `okf-standard/references/OKF-COMPATIBILITY.md`. |
| Product | `templates/` | Concept templates (`{{placeholders}}`): decision, ADR, runbook, playbook, system, API, table, metric, computation, term, policy, view, reference, project, fragment, conflict log. Generated copy of `okf-standard/templates/`. |
| Product | `.claude-plugin/marketplace.json` | This repo acts as a plugin marketplace. |
| Product build | `justfile`, `build/`, `.github/workflows/`, `release-please-config.json` | Builds the packages and the root copies (`just copies`), and checks everything (`just test`, each check a named step of `build/checks.py`, and `just lint`); CI runs the checks on every pull request, and release-please proposes each release from the squash-merged pull request titles ([ADR-0036](knowledge/base/decisions/DEC-0005-release-please.md)). |
| Product build | `build/` | Platform package exporters (Copilot, M365) and the M365 agent's configuration. |
| Product build | `tests/`, `examples/` | Test fixtures, the Google fixtures and a conformant example bundle (`examples/knowledge/`). |
| Knowledge | `knowledge/` | The project's own knowledge (a conformant OKF bundle with the ADRs behind every decision). |
| Workspace | `.claude/`, `.agents/`, `.beads/`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` | How agents operate in this repo: the skill links, the issue tracker and the context files. |

## Installing the plugin

From Claude Code (repo published on GitHub):

```
/plugin marketplace add <owner>/j3r3-okf-builder
/plugin install okf-builder@j3r3-okf-builder
```

Locally, without publishing:

```
claude --plugin-dir ./plugin/okf-builder
```

In Cowork: load the `.plugin` file built by `just plugin` (or the one delivered in the chat).

The plugin also ships the **`knowledge-architect`** agent (`plugin/okf-builder/agents/knowledge-architect.md`): it works through the skills to capture fragments, distill them with you approving each change set, keep the Conflict Log, and answer from the bundle. It never marks a concept as verified ([ADR-0013](knowledge/base/decisions/architecture/ADR-0013-agent-projections.md)).

## Using it in a project

```
okf-init        → creates knowledge/ (index.md, log.md, project.md, subdirectories)
okf-capture     → "document this decision / create a runbook / register this service"
okf-fragment    → "capture this meeting / save this transcript" as a fragment, recorded as it happened
okf-distill     → proposes what a fragment changes in the bundle; applies only what you approve
okf-review      → double check: changes since the last review, open conflicts, unverified drafts
okf-lint        → validates spec + profile (CI-ready: uv run tools/okf/okf_lint.py knowledge --strict)
okf-index       → regenerates index.md from the frontmatter
okf-ask         → "why did we decide X?" by navigating the bundle and citing trust level
okf-migrate     → detects the version and migrates 0.1 ↔ 0.2 (always --dry-run first)
okf-projection  → creates, checks, refreshes and renders the projections in projections/; applies only what you approve
```

### Fragments and distillation

A meeting, transcript or chat is first kept as a **fragment** in `knowledge/fragments/`, exactly as it happened, with its date, origin and participants. `okf-distill` then reads the fragment against the concepts it touches and proposes a change set: additions, confirmations, updates, refutations (an outdated concept is deprecated and linked to its replacement) and conflicts. Nothing is applied until a person approves it, and conflicts go to the bundle's one Conflict Log, where `okf-review` records who decided each one. Approving a change set never marks a concept as verified ([ADR-0024](knowledge/base/decisions/standard/SDR-0017-fragment-capture-field-backfill.md)).

## Running the scripts directly

```bash
uv run plugin/okf-builder/skills/okf-standard/scripts/okf_init.py  --root . --title "My project" --description "…" --actor human:<id>
uv run plugin/okf-builder/skills/okf-standard/scripts/okf_lint.py  knowledge [--json] [--strict] [--no-profile]
uv run plugin/okf-builder/skills/okf-standard/scripts/okf_index.py knowledge [--check] [--dir decisions]
uv run plugin/okf-builder/skills/okf-standard/scripts/okf_migrate.py knowledge --to 0.2 --dry-run
uv run plugin/okf-builder/skills/okf-standard/scripts/okf_profile.py knowledge [--json]
uv run plugin/okf-builder/skills/okf-standard/scripts/okf_audit.py knowledge [--since <ref>] [--json]
uv run plugin/okf-builder/skills/okf-standard/scripts/okf_obsidian.py knowledge [--force]
```

`okf_obsidian.py` writes the Obsidian viewer setup of a bundle ([ADR-0032](knowledge/base/decisions/architecture/ADR-0032-obsidian-viewer-setup.md)): `.obsidian/app.json`, `.obsidian/.gitignore` and `knowledge.base`, so the bundle opens in Obsidian as a vault with Bases views over `base/` and `fragments/`; it never overwrites a file without `--force`. This repository commits its own (`just obsidian`).

`okf-lint` reports a credential committed in a bundle file as `SECRET_IN_BUNDLE`, a quick check. For pre-commit and CI use [gitleaks](https://github.com/gitleaks/gitleaks), the thorough scanner: `just secrets` runs `gitleaks dir` over this repo's bundles.

## Using it with GitHub Copilot (and other agents)

The skills follow the [Agent Skills](https://agentskills.io) standard, which Copilot discovers in `.github/skills/` (VS Code agent mode, Copilot CLI, coding agent). `just copilot` builds `dist/copilot/` with:

- `.github/skills/okf-*/` — the 11 skills with scripts and templates, paths rewritten (no `${CLAUDE_PLUGIN_ROOT}`).
- `.github/agents/okf.agent.md` — the `@okf` custom agent.
- `AGENTS.okf.md` — a fragment for `AGENTS.md`.

Copy `dist/copilot/.` into the root of the target repo. Claude Code also reads `.github/skills/`, so a repo with the pack works with both, without the plugin. Neutral variant: `python3 build/export_copilot.py --skills-dir .agents/skills`.

## Using it with Microsoft 365 Copilot

M365 Copilot (Cowork, Copilot Studio, Agent Builder) accepts Agent Skills in the same `SKILL.md` format. `just m365` builds:

- `dist/m365/okf-builder-m365.zip` — an **M365 Copilot Cowork** plugin (manifest v1.28 + 11 self-contained skills). Uploaded by an admin (Manage apps → Upload custom app) or personally with `atk install --file-path … --scope Personal`. Cowork currently requires the Frontier program.
- `dist/m365/okf-knowledge-architect-m365.zip` — the **knowledge-architect declarative agent**, generated from the plugin agent, with its own copy of the 8 skills chosen in `build/m365-agent.json`; the Claude agent preloads all 11. A separate package, installed the same way; not yet tested in a tenant.
- `dist/m365/skills/okf-*.zip` — one zip per skill for **Copilot Studio / Agent Builder** → Build → Skills → Upload a skill (GA).

M365 Copilot reads the knowledge (`knowledge/`) from its one source ([ADR-0014](knowledge/base/decisions/standard/SDR-0008-knowledge-repository-storage.md)): a Git repository through the GitHub Cloud Knowledge connector, which indexes `.md`, or a SharePoint library for teams without Git. Microsoft does not document `.md` as a SharePoint knowledge file type, so check it in your tenant.
