---
name: okf-lint
description: Validates that knowledge/ complies with the OKF v0.2 spec, its OKF profile (knowledge/3.0, or the older knowledge/2.0 it reports as outdated) and its Domain Profile (the built-in one, the profiles it extends and base/profile.md), and lists what that Domain Profile puts in force at a path (frontmatter, type, index/log, layers, actors, ISO 8601, links, staleness, out-of-date indexes, local types, families, rules, aliases). Use when the user says "validate the knowledge", "okf lint", "check the bundle", "is knowledge/ well formed?", "what does the Domain Profile require here?", or before a commit/PR that touches knowledge/.

# okf-lint

> **Paths.** `<skills>` is the directory that holds the `okf-*` skills (the parent of this skill): `${CLAUDE_PLUGIN_ROOT}/skills` in the Claude plugin; `.claude/skills`, `.agents/skills`, `.github/skills` or `.gemini/skills` in a repo. The scripts live in `<skills>/okf-standard/scripts/` and the templates in `<skills>/okf-standard/templates/`. Without uv, `python3` works if PyYAML is installed.

## Steps

1. Run:
   ```bash
   uv run "<skills>/okf-standard/scripts/okf_lint.py" [<bundle>] [--json] [--strict] [--no-profile] [--okf-version auto|0.1|0.2] [--run-validators]
   uv run "<skills>/okf-standard/scripts/okf_lint.py" <bundle> --profiles [<path>] [--json]
   ```
   Without an argument it searches for `knowledge/` upwards from the cwd. `--okf-version auto` (the default) uses `okf_version` from the root `index.md` or infers it; the last line of output reads `OKF <version> (<origin>)`. The OKF profile is `okf_profile` in the root `index.md` (missing means knowledge/2.0, the older OKF profile); each bundle is validated by its own OKF profile's layout, and `projections/` is skipped entirely (not OKF).
   - In a knowledge/3.0 bundle each concept is also checked, aliases resolved first, against the Domain Profile in force for its type and its directory: the built-in Domain Profile, each profile `base/profile.md` lists in `extends`, then `base/profile.md` itself. `--no-profile` applies none of it and validates only the spec (useful for external bundles).
   - `--profiles [<path>]` lists what is in force at a bundle path or directory (`/base/clients/`, default `/`): the types allowed, each one's fields and requirements, the rules, the aliases, the validators and the mapped questions, each with the layer that declared it (`built-in`, an `extends` reference, `base/profile.md`). `--json` gives the same as data; the other skills read the Domain Profile this way. It exits 1 when the Domain Profile has a structural error.
   - `--run-validators` runs the commands of the Domain Profile's `validator` entries. **Never pass it without the person's say**: name each validator and its command (from `--profiles`) and ask first, since a bundle's content never runs a command by default.
   - What lint leaves out, each with a `NOTICE`: the paths a root `.okfignore` matches (gitignore-style globs; `--json` lists them under `ignored`; it never excludes the reserved files, any `index.md` or `base/profile.md`: `cannot ignore <path>: reserved`), a **nested bundle** (a subdirectory other than `fragments/`, `base/` and `projections/` whose `index.md` declares its own `okf_version`; lint it on its own with `okf_lint.py <that directory>`), and a **non-OKF directory** (no `index.md`, and no Markdown file in it has a frontmatter with a key of the spec, such as `type`, `title`, `description` or `generated`: `<dir>/ is not OKF: N Markdown files`). In a knowledge/3.0 bundle a non-OKF directory outside `fragments/` and `base/` is instead one `PROFILE_OUTSIDE_LAYER` error for the whole directory (ADR-0018). A directory that mixes concepts and plain files keeps its per-file findings.
2. Interpret the output:
   - Each finding names its **rule layer** (`layer` in `--json`; not the bundle layers `fragments/`/`base/`/`projections/`, nor the Domain Profile layers `--json` names as `source`): `spec` (the OKF spec, all `--no-profile` still checks), `okf-profile` (knowledge/3.0 or 2.0 itself: `PROFILE_OKF_VERSION`, `PROFILE_NO_*`, `PROFILE_PROJECT_TYPE`, `PROFILE_MANY_*`, `PROFILE_OUTSIDE_LAYER`, `NAME_KEBAB`, `NO_OKF_VERSION`, and the audit checks `FRAGMENT_UNCITED`, `SECTION_EMPTY`, `VERIFIED_STALE`, `FRAGMENT_MATERIAL_CHANGED`, `FRAGMENT_NO_LEDGER`, `LEDGER_GAP`) or `domain-profile` (what the Domain Profile in force declares, built-in included). The last line gives the totals and, in parentheses, errors/warnings per rule layer: `spec 0/2 · okf-profile 0/0 · domain-profile 0/0`; `--json` gives them under `by_layer`.
   - A root `okf_profile` okf-builder does not ship (neither knowledge/2.0 nor 3.0) gets the `spec` checks only: what the other two rule layers find is one `NOTICE profile <name> is not one okf-builder ships ...` with the count and codes, listed in `--json` under `skipped`; it never fails `--strict`.
   - `ERROR` breaks conformance (no frontmatter, no `type`, invalid YAML, invalid `status`, malformed `index`/`log`, missing `index.md`/`log.md`/`project.md`, missing `generated`, Attested Computation without `runtime`/computation).
   - `WARN` is guidance: broken links (`BROKEN_LINK`), `STALE`, `INDEX_STALE`, no `description`, malformed actors or dates, names that aren't kebab-case.
   - Versions: `LEGACY_TIMESTAMP`/`LEGACY_CITATIONS` (0.1 forms in a 0.2 bundle), `V02_FIELD_IN_V01` (0.2 keys in a 0.1 bundle, kept as they are), `MIXED_VERSIONS` (half migrated), `NO_OKF_VERSION` (root doesn't declare a version), `UNSUPPORTED_OKF_VERSION` (root declares a version other than 0.1 or 0.2; the message names it and the version inferred instead), `VERSION_MISMATCH`. All of them are resolved with `okf-migrate` or by declaring `okf_version`.
   - **knowledge/3.0 layout** (errors): `PROFILE_OUTSIDE_LAYER` (a concept at the root other than `project.md` and the Conflict Log, or a directory that is not `fragments/`, `base/` or `projections/`; move it under `base/`), `PROFILE_OKF_VERSION`, `PROFILE_NO_INDEX`, `PROFILE_NO_LOG`, `PROFILE_NO_PROJECT`, `PROFILE_PROJECT_TYPE`, `PROFILE_MANY_PROJECTS`, `PROFILE_MANY_CONFLICT_LOGS`, `PROFILE_NO_GENERATED` (`PROFILE_NO_TIMESTAMP` in 0.1). `QUESTION_REVIEW_DUE` (warning): an open question past its `review_on`.
   - **Domain Profile structure** (errors, on the Domain Profile file named): `PROFILE_INVALID` (a key outside the §4.1 schema, a local type extending an undeclared type, an alias for an undeclared name, an `extends` cycle), `PROFILE_DUPLICATE_ID` (the same type, family, rule or alias id from two sources), `PROFILE_REDEFINED` (an extension changes, removes or lowers an inherited item), `PROFILE_UNREADABLE` (an `extends` reference that cannot be read: a missing path, an unknown commit, or a URL, which is not read), `PROFILE_MISPLACED` (a Domain Profile anywhere but `base/profile.md`). Fix the Domain Profile with `okf-capture`, after the person approves.
   - **A concept against the Domain Profile**, at the level the Domain Profile declares, `--json` naming the `source` layer: `PROFILE_REQUIRED`, `PROFILE_ENUM`, `PROFILE_FIELD_TYPE`, `PROFILE_FIXED`, `PROFILE_FORBIDDEN`, `PROFILE_RULE`, `PROFILE_TYPE_NOT_ALLOWED` (a type the directory's family does not allow), and `PROFILE_UNKNOWN_KEY` (warning, only in a bundle with a `base/profile.md`: a key no layer declares for the type). The built-in Domain Profile keeps its own codes: `FRAGMENT_NO_FIELD` and `QUESTION_NO_FIELD` (warnings), `BAD_DISTILLATION_STATUS` and `BAD_QUESTION_STATUS` (errors), `QUESTION_NO_ANSWER` (warning), `BAD_ACTOR` and `BAD_ISO` (warnings), and `BAD_MATERIAL` and `BAD_REPOSITORY` (warnings): a fragment's `material` item that is not `{ path, sha256 }` with a 64-hex `sha256`, or a `repository` that is not `{ url, commit }` with a text `url` and a full 40-hex `commit` (a value YAML reads as a number is not text: quote it). A `map` field of a local type is checked the same way: a value that is not a map, a missing required key or a key of another type, under the field's code or `PROFILE_FIELD_TYPE`; `--profiles` lists its keys. Fix the concept, never the Domain Profile to make the concept pass: friction with it goes to the person.
   - **Audit checks** (standard §7): `SECRET_IN_BUNDLE` (error, `spec`): a line of a bundle file, frontmatter or body, holds a credential (a JWT, a `Bearer` or `Authorization` value, a known token prefix such as `ghp_`, `glpat-`, `AKIA`, `sk-`, `xoxb-`, `AIza`, or a key naming a token, key, password or secret with a long value of letters and digits); it names the file and line, never the value, lint masks that value in every other finding and notice too, and `.okfignore` excludes a file from it. `FRAGMENT_UNCITED` (warning): a distilled fragment that no file under `base/` nor the Conflict Log cites by link, `sources` or `asked_in`, unless its ledger is complete. `FRAGMENT_NO_LEDGER` (warning): a distilled fragment whose `# Distillation` has no 4-column ledger table, or one with no rows; no date exemption. `LEDGER_GAP` (warning, `line` in `--json`): a ledger row whose Concept (the last column) is not bundle links, `tracker` or `no concept (<reason>)` with a reason without parentheses (an old `—` or an external URL included), or a `##` heading of `# Record` that no row's Item names (equal to it, or starting with it at a word boundary); a broken link there is only `BROKEN_LINK`, and leaves the ledger incomplete. A table in a code fence or an HTML comment is not the ledger. `SECTION_EMPTY` (warning, `line` in `--json`): a section of the concept's template (a local type is read as the type it extends) left empty or holding only placeholder text (a line that is wholly `{{...}}`, an HTML comment, `...` items, rows with empty cells). `VERIFIED_STALE` (warning): `generated.at` later than the latest `human:` verification, both dates named. `FRAGMENT_MATERIAL_CHANGED` (error, `okf-profile`, fails without `--strict`): a fragment's `material` file in the bundle whose SHA-256 is not the recorded one, so the record's source changed after capture; a file `.okfignore` excludes is still hashed. A material file that is absent, outside the bundle (`../`) or in a nested bundle is a `NOTICE` and is never read; lint never fetches a `repository`.
   - **Metrics**: `--json` always carries `metrics`: `count_per_code` (reported findings, not `skipped`), `concepts_by_trust` (`unverified`, `machine-confirmed`, `human-reviewed`), `fragments` (`by_status`, and `oldest_pending_days` from `occurred_at`, else `generated.at`; `null` with none pending) and, when more than a quarter of at least 4 `stale_after` dates fall in one ISO week, `stale_after_cluster` (each such week with its count). They are figures, never findings.
   - **Validators**: `PROFILE_VALIDATOR` (error) is a validator whose command failed with `--run-validators`, its output masked and truncated; without the flag each validator is a `NOTICE validator <name> not run (use --run-validators)`.
   - `NOTICE profile knowledge/2.0 is outdated` (`"profile_outdated": true` in `--json`): the bundle uses the older OKF profile. A `base/profile.md` in it is ignored with a notice too. Notices are neither WARN nor ERROR and never fail `--strict`; offer the migration to knowledge/3.0 with the `okf-migrate` skill, applied only after the person confirms.
3. Propose concrete fixes per file. For `INDEX_STALE` run `okf-index`. For `STALE` list the concepts and ask the user to decide: renew `stale_after`, update the content or deprecate. For `BROKEN_LINK` offer `okf-capture` for the missing concept. For `SECRET_IN_BUNDLE` tell the person to remove the value, rotate the credential (it stays in the history) and scan the history with gitleaks; never print the value. For `FRAGMENT_UNCITED` cite the fragment in `sources` of the concepts its knowledge went to, or complete its ledger. For `FRAGMENT_NO_LEDGER` and `LEDGER_GAP` fill the ledger from what the distillation did (the concepts that cite the fragment, the log, the tracker items): links, `tracker` or `no concept (<reason>)`; ask the person when it is not known, and never edit `# Record`. For `SECTION_EMPTY` fill the section from what is known or remove it; never invent people or facts. For `VERIFIED_STALE` ask for a new verification with `okf-review`; never add or remove a `verified` entry yourself. For `FRAGMENT_MATERIAL_CHANGED` ask the person whether the file was altered: restore it as captured (from git), or capture the new version as a new fragment; never rewrite `sha256` to make it pass.
4. If the user asks for it, apply the mechanical fixes (date format, `status`, regenerating indexes) and run again until there are 0 errors. Don't touch semantic content, the Domain Profile or `verified` without confirmation.
5. To add it to CI, propose:
   ```yaml
   # .github/workflows/okf-lint.yml
   - uses: astral-sh/setup-uv@v6
   - run: uv run tools/okf/scripts/okf_lint.py knowledge --strict
   - uses: gitleaks/gitleaks-action@v2   # the thorough secret scanner; SECRET_IN_BUNDLE is a quick check
   ```
   copying `okf-standard/scripts/okf_common.py`, `okf_profile.py` and `okf_lint.py` into the repo's `tools/okf/scripts/` and `okf-standard/profiles/knowledge-3.0.md` into `tools/okf/profiles/` (`uv run` installs PyYAML). CI never passes `--run-validators` unless the person asks for it.
