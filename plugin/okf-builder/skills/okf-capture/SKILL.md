# okf-capture

> **Paths.** `<skills>` is the directory that holds the `okf-*` skills (the parent of this skill): `${CLAUDE_PLUGIN_ROOT}/skills` in the Claude plugin; `.claude/skills`, `.agents/skills`, `.github/skills` or `.gemini/skills` in a repo. The scripts live in `<skills>/okf-standard/scripts/` and the templates in `<skills>/okf-standard/templates/`. Without uv, `python3` works if PyYAML is installed.

Turns knowledge (a decision, procedure, component or definition) into an OKF concept that is correctly typed, linked and logged.

## Steps

1. **Find the bundle** (`knowledge/index.md`, searching upwards from the cwd; if there is none, propose `okf-init` and stop), **its version** (`okf_version` in the root `index.md`; if missing, `okf_lint.py --json` → `okf_version`) and **its OKF profile** (`okf_profile` in the root `index.md`; if missing, knowledge/2.0, the older OKF profile). Write in that version and in that OKF profile's layout.
   - **knowledge/2.0 bundle**: the typed directories sit at the root; drop the `base/` prefix from every directory, bundle path and `--dir` below (`decisions/`, `/decisions/x.md`, `--dir decisions`), never mix the two layouts, and offer the migration (`uv run "<skills>/okf-standard/scripts/okf_migrate.py" <bundle> --profile knowledge/3.0 --dry-run`, applied only after the person confirms).
   - **The Domain Profile in force** (knowledge/3.0; a knowledge/2.0 bundle has none): once the target directory is known, run `uv run "<skills>/okf-standard/scripts/okf_lint.py" <bundle> --profiles <target dir> --json` and read from it, not from `base/profile.md` by hand, what is in force there: the types allowed, each one's fields and requirements, the rules, the aliases and the mapped questions, each with the layer that declared it (built-in, an `extends` profile, `base/profile.md`).
2. **Classify**: pick the `type` and directory from the `okf-standard` table and the Domain Profile in force. A local type has no row in that table: it goes in the directory it declares (`directory`, in the Domain Profile that declares the type), else in that of the nearest type it extends that declares one (its `extends` chain in `--profiles`). Offer the types that fit the knowledge among those allowed in the target directory (`types_allowed`), the local types first (a local type that extends the type the table gives), each with the fields it declares and those it requires; a family that allows a standard type allows the local types that extend it. **Never relax the Domain Profile to make a concept fit** (no lowered level, no removed value, no skipped rule): when the knowledge fits no allowed type, raise it to the person with the three ways out of ADR-0026 decision 9: fit an existing type, propose a change to a type that almost fits, or declare a local type (see *The Domain Profile* below). Concepts go under `base/<dir>/`; never write a concept into `projections/` (derived, not OKF) or at the bundle root (only `project.md` and `conflict-log.md` live there). If the user doesn't say, infer it from the content and confirm it in one line. A meeting, transcript or chat to keep as it happened is not a concept: hand it to the `okf-fragment` skill and stop. Common cases:
   - "we decided…" → a decision: the type that fits what was decided among those of the Domain Profile in force that are a `Decision` (in `--profiles`, `Decision` and every type whose `extends` chain reaches it). `Architecture Decision` when it is about how a system is built ("we decided to use X instead of Y"), a local kind the bundle declares when one fits, plain `Decision` when no declared kind fits.
     - Template: `<skills>/okf-standard/templates/adr.md` for an Architecture Decision, `<skills>/okf-standard/templates/decision.md` for a Decision. A local kind has no template of its own: use the one of the nearest built-in type it extends (`adr.md` with `adr_id` when it extends Architecture Decision, `decision.md` with `decision_id` otherwise), write the kind's name in `type` and the title `<PREFIX>-NNNN: <title>` with the kind's prefix, and keep the template's tags.
     - File: `<PREFIX>-NNNN-slug.md` in the directory in force of the type (`base/decisions/architecture/` for an Architecture Decision, `base/decisions/` for a Decision, the directory a local kind declares, else that of the nearest type it extends). PREFIX is the prefix in force (`prefix` in `--profiles`: `ADR`, `DEC`, the one a local kind declares, else that of the nearest type it extends). NNNN is the highest number that prefix was ever given in the bundle plus one, 4 digits, read from the file names of the bundle's decisions and from every `formerly` value (the identifier a decision had before a move), so a number is never reused. The identifier `<PREFIX>-NNNN` goes in `decision_id` (`adr_id` in an Architecture Decision).
     - **knowledge/2.0 bundle**: it keeps `decisions/ADR-NNNN-slug.md` at the root.
   - "when alert X fires we…" → Runbook.
   - "service X does…, exposes…, depends on…" → System (+ API if there is a contract).
   - "X means…" → Term.
   - "metric X is computed…" → Metric + Attested Computation if there is sanctioned SQL/code.
   - "we don't know X yet", "who decides Y?" → Open Question (`base/questions/<kebab-slug>.md`, no ID; template `open-question.md`). Ask for its `owner` (the actor who must get it answered, `human:<id>`) and, when it came from a fragment, set `asked_in: /fragments/<file>`; a question raised outside any fragment cites its origin in `sources` and has no `asked_in`. It starts `question_status: open`; add `blocks` (the concepts it holds up) and `review_on` if the person gives them. Before creating it, look in `base/questions/` for the same question still open.
3. **Read the existing context** before writing: the `index.md` of the target directory and the concepts you will link to (systems, earlier decisions). Detect duplicates: if an equivalent concept already exists, propose updating it (and, if the decision changes, deprecate it and create the new one with `supersedes`/`superseded_by`). If the new knowledge answers an open question in `base/questions/`, the concept cites the question in `sources` (`resource: /base/questions/<slug>.md`), and the question gets `question_status: answered`, `answered_by` with the concept's bundle path, a `# Answer` that summarizes and links it, and a new `generated.at` (its `status` does not change; an **Update** log entry).
4. **Write** from the template `<skills>/okf-standard/templates/<type>.md`:
   - Replace every `{{...}}`. `actor` = whoever supplies the content: if the user dictates it and Claude only formats it, `human:<id>`; if Claude synthesizes it from the code/repo, `okf-builder/<model>`. `now` = UTC ISO 8601 `YYYY-MM-DDTHH:MM:SSZ`.
   - A local type has no template of its own: use the template of the standard type it extends (its `extends` chain in `--profiles`), set `type` to the local type and add the fields it declares that the person gives a value for. Fill every field the Domain Profile requires for the type in that directory, its families and rules included; ask the person for a value you do not have, never invent one.
   - Always `status: draft` on creation. Do **not** add `verified`.
   - **The bundle's own names** (the `aliases` in force): write a local name for a type or a field only when the existing concepts of that type already use it more than the declared name, and the declared name on a tie or when no concept uses a local one, since writing a local name no concept uses would rename the bundle's vocabulary. A type alias names exactly its target (a local name of `Client Meeting` is never a `Knowledge Fragment`). A value alias is written in reverse (`ingerido: false` for `distillation_status: pending`) only when the type is written with a local name and exactly one alias maps to that field and value. Lint reads every local name as the declared one.
   - `description`: one self-contained sentence.
   - Bundle-absolute links (`/base/systems/x.md`; the templates' example links already use `/base/...`). Link even if the target doesn't exist yet; list the pending links at the end.
   - If the content derives from sources (docs, tickets, URLs, repo files): `sources[]` with `resource` and `id`, and `[^id]` footnotes on the claims that need them. For repo files use repo-relative paths as `resource`.
   - Empty template sections: remove them or leave an explicit `TODO`, never placeholders.
   - **0.1 bundle**: after saving, run `uv run "<skills>/okf-standard/scripts/okf_migrate.py" <bundle> --to 0.1 --file <relative-path>` to convert `generated`→`timestamp` and `sources`→`# Citations`; never leave 0.2 keys in a 0.1 bundle.
5. **Log**: add an entry to `knowledge/log.md` under today's date (create the section if it doesn't exist, above the earlier ones): `* **Creation**: ...` / `* **Update**: ...` / `* **Deprecation**: ...`, with a link to the concept. If the directory has its own `log.md`, add it there too.
6. **Index and validate**:
   ```bash
   uv run "<skills>/okf-standard/scripts/okf_index.py" <bundle> --dir <the concept's directory>     # e.g. base/decisions/architecture
   uv run "<skills>/okf-standard/scripts/okf_lint.py" <bundle>
   ```
   One run per directory a concept was written to (`--dir base` for `base/profile.md`). It regenerates that directory's `index.md` and the one of every directory above it up to the bundle root, so a directory that is new is listed by its parent. Fix any ERROR before finishing.
7. **Close**: show the concept's path, its `type` and the pending links, and remind the user that it stays `draft` until a person adds `verified: { by: human:<id>, at: ... }` and moves it to `stable` (offer the recorded verification of `okf-review` if the user has reviewed it).

## The Domain Profile

Only when the person asks for it (a new local type, family, rule, alias or mapped question, or a fix), and in knowledge/3.0 only:

1. **Propose the exact change** to `base/profile.md`: the keys added, each with its reason, and the layer each one builds on (`--profiles --json` shows what is inherited). Composition only adds: never redefine, remove or lower an inherited item (that is `PROFILE_REDEFINED`); an inherited enum gains a value only through `by_type.<Type>.values.<field>`. **Apply nothing until the person approves.**
2. **Write it**: with no `base/profile.md`, create it from `<skills>/okf-standard/templates/domain-profile.md` (with a **Creation** log entry and `base/index.md` regenerated). Otherwise edit it in place: the new keys in the frontmatter, their justification in the body, a new `generated.at`, and an **Update** log entry naming each change; git keeps the history. Do not add `verified`.
3. **Validate**: `okf_lint.py <bundle>` reports no `PROFILE_INVALID`, `PROFILE_DUPLICATE_ID`, `PROFILE_REDEFINED`, `PROFILE_UNREADABLE` or `PROFILE_MISPLACED`, and `--profiles <dir>` shows the change in force. A concept the change now breaks is listed for the person; it is not edited without their approval.
4. **Refresh the Obsidian views**: when the change adds or removes an alias or a local type and the bundle has a `knowledge.base`, rerun the Obsidian viewer setup of the `okf-init` skill (its step 7) with `--force`, since its views read the aliases and local types in force when it was written; nothing else checks that they are current.

## Batch capture

If the user asks "document the services in this repo" or similar: take an inventory first (list of candidates with type and proposed path), confirm it, then create them one by one following steps 4–6. At most 15 concepts per batch without a new confirmation.
