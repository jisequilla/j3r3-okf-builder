---
name: okf-distill
description: Distills one pending knowledge fragment into the OKF bundle. Reads the concepts it touches, proposes a change set of additions, confirmations, updates, refutations and conflicts, with unanswered questions as open questions, action items listed for the tracker and knowledge that fits no type as a Domain Profile change, and applies it only after the person approves, opening conflicts in the Conflict Log. Use when the user says "distill this fragment", "what does this meeting change", "process the pending fragments", "okf distill", or after okf-fragment has captured an event. Also closes an operational instance into its parent through okf_close.py ("close this request", "close the instance", "okf close").
---

# okf-distill

> **Paths.** `<skills>` is the directory that holds the `okf-*` skills (the parent of this skill): `${CLAUDE_PLUGIN_ROOT}/skills` in the Claude plugin; `.claude/skills`, `.agents/skills`, `.github/skills` or `.gemini/skills` in a repo. The scripts live in `<skills>/okf-standard/scripts/` and the templates in `<skills>/okf-standard/templates/`. Without uv, `python3` works if PyYAML is installed.

Turns what a fragment records into changes to the bundle's concepts. It proposes; the person decides. Nothing is written before the person approves the change set, and approving a change set is not reviewing a concept: distillation never sets `verified`.

To close an operational instance into its parent, follow **Closing mode**, at the end of this skill, instead of these steps.

## Steps

1. **Find the bundle** (`knowledge/index.md`, searching upwards from the cwd; if there is none, propose `okf-init` and stop), **its version** (`okf_version` in the root `index.md`; if missing, `okf_lint.py --json` → `okf_version`) and **its OKF profile** (`okf_profile` in the root `index.md`; if missing, knowledge/2.0, the older OKF profile). Write in that version and in that OKF profile's layout.
   - **knowledge/2.0 bundle**: the typed directories sit at the root; drop the `base/` prefix from every directory, bundle path and `--dir` below (`/decisions/x.md`; indexes: `--dir decisions`, and `--dir fragments` when a fragment changed), never mix the two layouts, and offer the migration (`uv run "<skills>/okf-standard/scripts/okf_migrate.py" <bundle> --profile knowledge/3.0 --dry-run`, applied only after the person confirms).
   - **The Domain Profile in force** (knowledge/3.0; a knowledge/2.0 bundle has none): run `uv run "<skills>/okf-standard/scripts/okf_lint.py" <bundle> --profiles <dir> --json` for `/fragments/` and for each directory a change targets, and read from it, not from `base/profile.md` by hand, the types allowed there with their fields and requirements, the rules and the aliases. **Resolve the aliases when reading** fragments and concepts: a local type name is the type it stands for, a field alias the declared field, and a value alias whose `from` holds is its `to`, so a `Fragmento` with `ingerido: false` is a pending `Knowledge Fragment` when the aliases say so.
2. **Pick one fragment.** The one the person names, or list the pending ones and ask: the files in `fragments/` whose `distillation_status` is `pending`, aliases resolved (`grep -l "distillation_status: pending" <bundle>/fragments/*.md`, plus a `grep` for the `from` of each value alias whose `to` is `distillation_status: pending`, such as `ingerido: false`). One fragment per run. If it is `distilled`, say so and stop unless the person asks to distill it again; if it is `conflict`, point to `okf-review`.
3. **Read the context**: the root `index.md`, `base/index.md`, the `index.md` of each directory the fragment touches, the concepts it names or contradicts (systems, decisions, terms, runbooks) and the Conflict Log (`/conflict-log.md` unless the bundle places it elsewhere), so an open conflict is not opened twice. Read the fragment's `# Record`; never edit it.
4. **Route each item** of the record by what it is (ADR-0021), the rule for every item:

   | In the fragment | Goes to |
   |---|---|
   | A decision, a fact, a definition | A concept in `base/`, by one of the five kinds below |
   | A question nobody in the record answers | An *Addition* of an `Open Question` in `base/questions/<kebab-slug>.md` (template `open-question.md`), with `owner` (the actor who must get it answered, `human:<id>`; ask if the record does not name one), `question_status: open` and `asked_in: /fragments/<file>`; unless the same question is already open there, which makes it a Confirmation of that question |
   | An answer to a question open in `base/questions/` | An *Addition* or *Update* of the concept that holds the answer, citing the fragment and the question, plus an *Update* of the question that sets `question_status: answered` and `answered_by` (step 6) |
   | A proposal nobody has validated | A decision with `decision_status: proposed`, or an `Open Question`: propose one in the change set and let the person pick |
   | An action item (someone must do something) | Not a concept: the change set lists it under **To the tracker** with its owner and text. It is never written into `base/`; the person files it in the team's tracker, and no tracker is called. A concept may later link the tracker item |
   | Logistics, tone, commercial terms, small talk | Not items: they stay in the record |
   | Knowledge that fits no type the Domain Profile allows in its directory | A **Domain Profile** item of the change set: the change to `base/profile.md` (a local type, a field of a local type, a family, a rule, an alias or a mapped question), its reason and the record line behind it, with the concept that waits on it. Never relax the Domain Profile instead (ADR-0026 decision 9: fit an existing type, propose a change to one that almost fits, or declare a local type). In a knowledge/3.0 bundle without `base/profile.md`, the item proposes creating it from `<skills>/okf-standard/templates/domain-profile.md` |

   **Classify each knowledge item** into one of five kinds, each with its target concept (an existing path, or the type and path of a new one under `base/<dir>/`; never a concept in `projections/`, which is derived and not OKF, or at the bundle root, which holds only `project.md` and `conflict-log.md`):

   | Kind | When | Proposed change |
   |---|---|---|
   | Addition | The fragment brings knowledge the bundle lacks | A new concept, or a new part of one |
   | Confirmation | The fragment states what a concept already says | The fragment is added to the concept's `sources` |
   | Update | The fragment refines a concept and contradicts nothing | The concept is edited, with an **Update** log entry |
   | Refutation | The fragment makes a concept outdated and names or implies its replacement, and nobody in the record disputes it | The concept is deprecated and links to its replacement (for a decision, a new decision of the same type that supersedes it); a **Deprecation** log entry; no conflict is opened |
   | Conflict | The fragment contradicts a concept and it is unclear which is right: participants disagree, sources disagree, or the replacement is not known | A row in the Conflict Log |

   **When in doubt between refutation and conflict, it is a conflict.**
5. **Propose the change set** and stop: one table grouped by kind, with Item · Kind · Target concept · Proposed change · Evidence (speaker and timestamp in the record). Domain Profile items go in the table too, Kind `Domain Profile`, before the items that wait on them. Below the table, a **To the tracker** list: one line per action item, with its owner and text, for the person to file. Then the **Ledger** the fragment will get (step 7): one row per part of `# Record` (each `##` heading when it has them, else each paragraph or turn), with the concept it goes into, `tracker`, or `no concept (<reason>)` for what stays out (logistics, small talk) and why, so the person sees what is left out before approving. Ask the person to approve, change or reject each item of the table; the tracker list is not approved, only handed over. **Apply nothing until the person approves.** Rejected items are not applied and are recorded as `rejected`; an item the person drops gets `no concept (dropped by <actor>)` in the ledger.
6. **Apply the approved items** with the `okf-capture` rules (template `<skills>/okf-standard/templates/<type>.md`, `status: draft` on creation, actor `okf-builder/<model>`, one-sentence `description`, bundle-absolute links under `/base/...`, no placeholders, the fields the Domain Profile requires). A decision, of any type that is a `Decision`, takes the type, the directory, the prefix and the number `okf-capture` gives it, and the template of its type: `<skills>/okf-standard/templates/adr.md` for an Architecture Decision or a local kind that extends it, `<skills>/okf-standard/templates/decision.md` for a plain Decision or any other local kind. **The bundle's own names** (the `aliases` in force): write a local name for a type or a field only when the existing concepts of that type already use it more than the declared name, and the declared name on a tie or when no concept uses a local one, since writing a local name no concept uses would rename the bundle's vocabulary. A type alias names exactly its target (a local name of `Client Meeting` is never a `Knowledge Fragment`). A value alias is written in reverse (`ingerido: false` for `distillation_status: pending`) only when the type is written with a local name and exactly one alias maps to that field and value. Lint reads every local name as the declared one. Every concept created, confirmed, updated or deprecated cites the fragment in `sources` (`{ id: <id>, resource: /fragments/<file>, title: ... }`) with `[^id]` footnotes on the claims it supports.
   - **Addition**: create the concept, or add the part to an existing one and update its `generated`. An `Open Question` follows its template: `# Question`, `# Why it matters` (link the concepts in `blocks`), `# What is known`, and an empty `# Answer`.
   - **Answer to an open question**: the concept that holds the answer is created or updated as above and cites both the fragment and the question (`resource: /base/questions/<slug>.md`) in `sources`. The question is then updated: `question_status: answered`, `answered_by` with that concept's bundle path, a `# Answer` that summarizes and links it, the fragment added to its `sources`, and a new `generated.at`. Its `status` does not change and it is never deleted.
   - **Confirmation**: add the fragment to the concept's `sources` and attach its footnote to the sentence that already states the confirmed claim. Write no new sentence: if no sentence states it, the item is an Update. Update `generated` (`by`, `at`) and leave `verified` as it is, so the gap since the last verification stays visible.
   - **Update**: edit the concept and update `generated` (`by`, `at`); leave `verified` as it is (the gap between `verified` and `generated.at` is information).
   - **Refutation**: set `status: deprecated` on the outdated concept and link its replacement in the body; never delete it. For a decision (any type that is a `Decision`), create the new decision of the same type with `supersedes`, and give the old one `decision_status: superseded` and `superseded_by`. No Conflict Log row.
   - **Conflict**: the concept in dispute is not changed. Add a row to the Conflict Log; if the bundle has none, create `conflict-log.md` at the bundle root from `<skills>/okf-standard/templates/conflict-log.md` (with a **Creation** log entry). Row: `C-NNN` (highest existing + 1, three digits) · source (a link to the fragment, `/fragments/<file>`) · description (who or what says each side) · kind (participants disagree, sources disagree, contradiction with an accepted decision, replacement unknown) · resolution (empty, or the one proposed) · state `open`, or `proposed` when a resolution awaits a person · decided `—`.
   - **Domain Profile**: apply an approved item first, so the concepts that wait on it are written against it: with no `base/profile.md`, create it from `<skills>/okf-standard/templates/domain-profile.md` (a **Creation** log entry, `base/index.md` regenerated); otherwise edit it in place, the keys in the frontmatter and their justification in the body, a new `generated.at` and an **Update** log entry naming each change. It cites the fragment in `sources`. Composition only adds: never redefine, remove or lower an inherited item. Then `okf_lint.py <bundle>` shows no `PROFILE_INVALID`, `PROFILE_DUPLICATE_ID` or `PROFILE_REDEFINED`. A Domain Profile item the person rejects leaves the concepts that wait on it unwritten, recorded as `rejected`.
   - **0.1 bundle**: after saving each new or changed concept, run `uv run "<skills>/okf-standard/scripts/okf_migrate.py" <bundle> --to 0.1 --file <relative-path>`; 0.1 has no `status`, so a deprecated concept says so in the first line of its body, with the link to its replacement.
7. **Fill the fragment's `# Distillation`** with the approved ledger: one row per part of `# Record`, nothing left unaccounted for, with Item (a `##` heading of the record named by its text) · Kind · Outcome (`applied`, `rejected`, `open: C-NNN` or `proposed: C-NNN`, matching the row's state, and `not distilled` for an action item, whose Kind is `—`) · Concept: the link(s) to the concept(s) it went into, `tracker` for an action item filed in the team's tracker, or `no concept (<reason>)`. Lint warns on a distilled fragment without this table (`FRAGMENT_NO_LEDGER`) and on a row or `##` heading left unaccounted for (`LEDGER_GAP`). Set `distillation_status: distilled`, or `conflict` while any of its conflicts is `open` or `proposed`, in the fragment's own names: a fragment that carries a value alias of it (`ingerido: false`) gets the alias for the new value when exactly one maps to it (`ingerido: true`), and otherwise the local key is replaced by `distillation_status: <value>`. Nothing else in the fragment changes.
8. **Never add `verified`** and never move a concept to `stable`, even if the person approved the change set: that is a separate, explicit review (`okf-review`).
9. **Log** under today's date in `knowledge/log.md` (and the directory's own `log.md` if it has one), each linking its concept and the fragment: `* **Creation**: ...`, `* **Update**: ...` (also for confirmations), `* **Deprecation**: ... superseded by ...`, `* **Conflict**: C-NNN opened in the conflict log from <fragment>`, linking both. Use only these labels. The person's approval goes inside the entries (`approved by human:<id>`), never under a label of its own.
10. **Index and validate**:
    ```bash
    uv run "<skills>/okf-standard/scripts/okf_index.py" <bundle> --dir <directory>     # once per directory of a concept touched, e.g. base/decisions/architecture
    uv run "<skills>/okf-standard/scripts/okf_index.py" <bundle> --dir fragments
    uv run "<skills>/okf-standard/scripts/okf_lint.py" <bundle>
    ```
    Each run regenerates that directory's `index.md` and the one of every directory above it up to the bundle root, so a directory that is new is listed by its parent. Fix any ERROR before finishing.
11. **Close**: list what was applied, rejected and left open (with the `C-NNN` IDs), the open questions created or answered, and the action items to file in the tracker, describing each change as it is in the files (from `git diff` when the bundle is in Git), never as smaller than it is; remind the person that the new and changed concepts stay `draft` and unverified, and point to `okf-review` to resolve the conflicts and review the concepts. If `projections/` holds projections, run `uv run "<skills>/okf-standard/scripts/okf_projection.py" <bundle> --json`, never with `--run-render` or `--record-hashes`, and list the projections to refresh: each `PROJ_DRIFT` whose ref names a concept this run created, changed or deprecated, and, from reading only the `refs` of their `projection.yaml`, the rendered projections in `not_checked` and the recomputable ones in `to_recompute` whose refs name one, as possibly stale (no render ran; recomputed by hand). Leave out the projections under `frozen`, and report the script's errors as they are. Change nothing in `projections/`, and point to `okf-projection` for the refresh.

## Closing mode

Closes an operational instance into its parent, the bundle its root `index.md` names in `parent`, one level up (standard §2.2, ADR-0039): a request a release holds closes into the release, and every path below is then the release's. `okf_close.py` checks the closing and writes it; sorting each concept is the person's and yours, never the script's. Nothing is written before the person approves.

1. **Check**: `uv run "<skills>/okf-standard/scripts/okf_close.py" <instance> --json`. With any blocker, show it and stop: `PENDING_FRAGMENT` (distill that fragment into the instance first, with the steps above), `CHILD_OPEN` (close that instance first), `PARENT_CLOSED`, `ALREADY_CLOSED` or `NOT_INSTANCE`. Otherwise the report lists `concepts` (each with `from_parent`, its bundle path from the parent, and `parent_same_path`), the open `questions` and the open or proposed `conflicts`.
2. **Loose ends**: ask the person, for each open question and conflict, whether it is settled now or carried up. One settled now is answered, dropped, resolved or dismissed inside the instance under the usual rules (the steps above, `okf-review`), before the closing goes on.
3. **Sort each concept** against the parent, reading the parent's concept at `parent_same_path` and the ones it names:

   | Outcome | When | In the parent |
   |---|---|---|
   | **promote** | Lasting knowledge | An Addition (a new concept, `status: draft`, no `verified`, even when the instance's was verified), or a Confirmation or Update of the concept it states or refines, or a Refutation when it outdates one undisputed; the parent concept's `verified` is never touched |
   | **conflict** | It contradicts the parent and it is unclear which is right | A row in the parent's Conflict Log, created from `<skills>/okf-standard/templates/conflict-log.md` if there is none, its Source the closing fragment; nothing in the instance changes |
   | **stays** | It is about this unit of work only | Nothing |

   When in doubt between promote and conflict, it is a conflict.
4. **Propose the change set** and stop: one row per concept (Concept · Outcome · Target in the parent · Proposed change · Why), then each question and conflict to carry with the parent item it becomes. Apply nothing until the person approves; a rejected promote stays.
5. **Apply in the parent**, with the rules of steps 6, 9 and 10 above:
   - each promoted concept cites the instance concept in `sources` (`{ id: <id>, resource: <from_parent>, title: ... }`) and in a footnote;
   - each carried question becomes an Open Question of the parent's `base/questions/`, its `owner` kept, `question_status: open`, `asked_in` and a `sources` entry its `from_parent`;
   - each carried conflict becomes an `open` row of the parent's Conflict Log, its Source the closing fragment and its Description linking the instance's Conflict Log (`/<kind directory>/<id>/conflict-log.md`).

   Write nothing in the instance: the script writes its carried values and its closing.
6. **Write the closing fragment** in the parent's `fragments/` (`<date>-closing-<id>.md`, template `<skills>/okf-standard/templates/fragment.md`): `origin: closing of <Kind> <id>`, `participants` the approver and you, and a `# Record` with one `##` per instance concept, and per carried conflict, holding the proposal and the decision. Its `# Distillation` ledger has one row per instance concept: Kind `promote`, `conflict` or `stays`; Outcome as in step 7 above; Concept the instance concept linked down from the parent (`/<kind directory>/<id>/base/...`), plus the parent concept for promote. Each carried conflict gets a row of its own: Kind `conflict`, Outcome `open: C-NNN` (its row in the parent's Conflict Log), Concept the instance's Conflict Log linked down (`/<kind directory>/<id>/conflict-log.md`) plus the parent's Conflict Log. Its `distillation_status` is `distilled`: the conflicts it opens in the parent stay open in the parent's Conflict Log, not in the fragment. Links run down only: nothing in the instance links its parent, which it names as a path in code.
7. **Close**: run `uv run "<skills>/okf-standard/scripts/okf_close.py" <instance> --apply --fragment /fragments/<file>.md --by human:<approver> --actor okf-builder/<model> --carry base/questions/<q>.md=/base/questions/<q>.md --carry C-001=C-NNN --dry-run`, show the writes, then run it without `--dry-run`. It checks the ledger against the concepts, each promoted concept's source, each carry target and its link back, and writes nothing when one fails: fix the parent and run it again. Once it passes, the instance is `state: closed` with `closed_at`, each carried item says `carried` and names its parent item, an instance fragment whose conflicts are all carried is `distilled`, and both bundles' indexes are regenerated. An exit 3 means the closing is written only in part: show its ERROR lines, finish by hand what they name (for the indexes, run `okf_index.py` on the bundle named) and never run `--apply` again.
8. **Log and validate**: a **Closing** entry in the instance's `log.md` and an **Update** entry in the parent's, naming the instance and linking the closing fragment, then `uv run "<skills>/okf-standard/scripts/okf_lint.py" <parent>`: fix any ERROR, and no rule-16 code may remain.
