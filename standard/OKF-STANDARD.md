# OKF standard for projects (`knowledge/` profile)

**Profile version:** 3.0 · **Base:** Google's Open Knowledge Format (OKF) v0.2 ·
**Reference spec:** https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf

This document defines the `knowledge/3.0` profile: how a project's knowledge is organized inside its own repository, in a `knowledge/` folder, so that it is a conformant OKF *bundle* that people and agents can consume (Claude Code, Cowork, Knowledge Catalog, any markdown indexer).

---

## 1. Principles

1. **One repo, one domain bundle.** `knowledge/` is the root of the repo's bundle, and the operational bundles it holds are bundles of their own inside it (§2.2). A concept's path within its bundle is its identity.
2. **Only markdown + YAML frontmatter.** No SDK, no runtime. `cat` is enough to read it; `git` to distribute it.
3. **`type` is the only required field.** Everything else is recommended, never a reason for rejection.
4. **Progressive disclosure.** Every directory of the bundle has an `index.md`; an agent starts at the root and goes down only where it needs to. `projections/` is not OKF content and needs no `index.md`.
5. **Traceability first.** Every concept generated by an agent carries `generated`; every concept reviewed by a person carries `verified` with a `human:` actor.
6. **Links form the graph.** Relationships (depends-on, joins-with, supersedes) are expressed with markdown links and prose, not with special fields.
7. **Three layers.** `fragments/` is the record: events as they happened, immutable after capture. `base/` is the knowledge: OKF concepts that state the current state in the present tense, with their sources. `projections/` is the derivation: what is derived from the base for a reader; it is not OKF.

## 2. Directory structure

```
knowledge/
├── index.md                 # Bundle root. The only index.md with frontmatter (okf_version, okf_profile).
├── log.md                   # Chronological history of the bundle (most recent first).
├── project.md               # type: Project — project overview: purpose, scope, team, key links.
├── conflict-log.md          # type: Conflict Log — the bundle's conflict register; created with the first conflict.
├── requests/                # Optional: the instances of an operational kind the Domain Profile declares (§2.2), one bundle each.
│   ├── index.md
│   └── <id>/                # An operational bundle: index.md, log.md, project.md, fragments/, base/, projections/.
├── fragments/               # Record layer. type: Knowledge Fragment — records of events (YYYY-MM-DD-slug.md), distilled into base/.
│   └── index.md
├── base/                    # Knowledge layer: organised by type (the usual directories below) or by domain.
│   ├── index.md
│   ├── profile.md           # type: Domain Profile — optional, at most one per bundle: the types, families and rules the bundle declares (§4.1).
│   ├── architecture/        # Views, C4 context, diagrams, principles.
│   │   ├── index.md
│   │   └── overview.md
│   ├── decisions/           # ADRs (Architecture Decision Records).
│   │   ├── index.md
│   │   └── ADR-0001-....md
│   ├── domain/              # Glossary and business concepts.
│   │   ├── index.md
│   │   └── glossary.md
│   ├── systems/             # Components, services, deployable modules.
│   │   └── index.md
│   ├── apis/                # API contracts (they reference OpenAPI/Proto, they don't replace them).
│   │   └── index.md
│   ├── data/                # Datasets, tables, schemas, join paths.
│   │   └── index.md
│   ├── metrics/             # Metric/KPI definitions; they link to attested computations.
│   │   └── index.md
│   ├── computations/        # type: Attested Computation (sanctioned SQL/dbt/python).
│   │   └── index.md
│   ├── runbooks/            # Operations: incidents, deployments, rollback.
│   │   └── index.md
│   ├── playbooks/           # Business/team procedures (onboarding, releases).
│   │   └── index.md
│   ├── policies/            # Rules, standards, compliance, security.
│   │   └── index.md
│   ├── references/          # OKF convention §6.3: mirrored external material, execution skills, attesters.
│   │   ├── index.md
│   │   ├── skills/
│   │   └── attesters/
│   └── questions/           # type: Open Question — what the team does not know yet, with an owner (kebab-slug.md).
│       └── index.md
└── projections/             # Derivation layer, not OKF (ADR-0022): one directory per projection (§2.1).
    └── <slug>/
        ├── projection.yaml  # Manifest: lifecycle, nature, intent, refs; only a composed projection records their hashes.
        ├── content.md
        ├── render/
        └── deliverables/
```

**Rules:**

- All subdirectories are **optional** except `index.md`, `log.md` and `project.md` at the root. `okf-init` creates `fragments/`, `base/` and every typed directory empty (only with their `index.md`) so navigation is predictable across projects, and `projections/` empty (without an `index.md`, since it is not OKF); the ones that don't apply are removed.
- The root holds only what is about the bundle as a whole: `index.md`, `log.md`, `project.md`, `conflict-log.md`, the three layer directories `fragments/`, `base/` and `projections/`, and the directory of each operational kind the bundle may hold (§2.2).
- The profile's directory names are in English (ADR-0010); the `base/references/` subdirectory keeps the spec's `references/` name to interoperate with OKF consumers.
- File names: `kebab-case`, ASCII, no spaces. ADRs: `ADR-NNNN-short-title.md`.
- `index.md` and `log.md` are **reserved names** at any level: they are never used for a concept.
- A project can add its own directories under `base/` (e.g. `base/integrations/`, `base/security/`). They are documented in `base/index.md`.
- `base/` may be organised **by type**, as `okf-init` creates it, or **by domain** (`base/clients/`, `base/payments/`). The usual directory of each type (§4) is a default, not a rule. A bundle that wants to say what each directory holds declares it in the `families` of its Domain Profile, `base/profile.md` (§4.1); `base/index.md` lists `base/profile.md` with the directories.
- `projections/` is not OKF content: `okf-lint`, `okf-index` and `okf-ask` skip it, and no OKF tool treats a projection as a concept. A projection is a derivation with its own manifest and its own tools (ADR-0022, ADR-0031; §2.1), not knowledge. After a distillation, `okf-distill` reads only the `refs` of each `projection.yaml` to list the projections whose refs changed for refresh.
- **`.okfignore`** at the bundle root lists the paths that are not part of the bundle, one gitignore-style glob per line: a line that starts with `#` is a comment, `!` re-includes what an earlier line excluded, a trailing `/` matches directories only, a `/` at the start or inside a pattern anchors it at the root (otherwise it matches a name at any depth), and `**` crosses directories; the last matching line wins, and a path under an excluded directory cannot be re-included. `okf-lint` does not read what it matches and `okf-index` does not write there: it is no concept, is not counted, need not be listed in an `index.md`, and appears in `--json` under `ignored` and in one notice. `okf-migrate` never edits it: its files stay byte-identical, and the profile step (knowledge/2.0 → 3.0) leaves it where it is at the root, or moves it with a root directory it moves under `base/`, rewriting each `.okfignore` entry anchored under that directory to name the new place (`decisions/drafts/` → `base/decisions/drafts/`). It never excludes the root's reserved files (`index.md`, `log.md`, `project.md`, `conflict-log.md`, ADR-0018), the `index.md` of any directory or `base/profile.md`, nor `base/` while it holds `base/profile.md`: such a match is read as usual and reported as one notice, `cannot ignore <path>: reserved`. The file itself is not a concept. Hidden directories and `projections/` are skipped without it.
- **A nested bundle** is a subdirectory other than `fragments/`, `base/` and `projections/` whose `index.md` declares its own `okf_version` (in its frontmatter, which an `index.md` below the root otherwise never has, §5.1). It is another bundle, not part of this one. An instance of an operational kind, in the directory its kind declares, is checked with the bundle that holds it (§2.2); any other nested bundle `okf-lint` skips as a whole with one notice naming its path, the parent `index.md` need not list it, a link into it is an ordinary link, and `okf-lint <that directory>` lints it on its own. `okf-index` and `okf-migrate` never write into a nested bundle, instance or not: `okf-index` lists it in the parent `index.md` and indexes it only when run on that directory.
- **What a fragment's content becomes** (ADR-0021), the routing `okf-distill` applies:

  | In the fragment | Goes to |
  |---|---|
  | A decision, a fact, a definition | A concept in `base/` (`okf-distill`) |
  | A question nobody has answered | An `Open Question` concept in `base/questions/` |
  | A proposal nobody has validated | An ADR with `decision_status: proposed`, or an open question |
  | An action item (someone must do something) | The team's tracker; the base never copies it, and a concept may link the tracker item |
  | Logistics, tone, commercial terms | Nothing: they stay in the fragment's record |
- **Writing in `base/`**: a concept states the current state in the present tense, with its sources; dated history goes to `log.md` and to the fragments, not into the prose. A concept with several topics, or longer than about 300 lines, is split.

### 2.1 Projections

A **projection** is a directory `projections/<slug>/` (ADR-0022): `projection.yaml`, its manifest; `content.md`, its content (for a recomputable projection, the procedure); `render/<renderer>.md`, one input per renderer, when it is rendered; and `deliverables/`, the rendered files, latest version only. It is not OKF: no OKF tool treats it as a concept (`okf-distill` reads only its `refs`), and its own tools are `okf_projection.py` and the `okf-projection` skill (ADR-0031).

**`projection.yaml`** (ADR-0022 decision 2):

| Key | Required | Meaning |
|---|---|---|
| `lifecycle` | Yes | `canonical` (here to stay; refreshed when its refs change), `deliverable` (versioned and shared outside), `transient` (one-shot; not committed) |
| `nature` | Yes | `rendered`, `composed` or `recomputable` (below) |
| `intent` | Yes | Audience, scope, tone and what to leave out; it guides every refresh |
| `refs` | Rendered and composed: yes | The base concepts and projections it derives from, as bundle paths: `/base/...`, or `/projections/<slug>` optionally with a file inside it; a composed projection records each as a one-line `{ path: ..., sha256: ... }` |
| `render` | Rendered: yes | The command that produces it from its refs, deterministically |
| `frozen` | No | `true` when the projection is archived: it keeps its last state and is no longer checked for drift |
| `versions` | Deliverable | One entry per delivered version: `version`, `date`, `commit`, and to whom it was sent |

**Dependency rule** (ADR-0022 decision 3): a projection references the base and projections at least as stable as itself: `canonical` → base and `canonical`; `deliverable` → base, `canonical` and `deliverable`; `transient` → anything. A ref to a file inside a projection takes that projection's lifecycle. Removing a transient projection can break nothing else.

**Drift by nature** (ADR-0022 decision 4). The check lists what drifted and never regenerates it; a refresh proposes the change and a person approves it. A frozen projection is not checked.

| Nature | What it is | How drift is checked |
|---|---|---|
| `rendered` | A deterministic function of its refs | Only with `--run-render`: `render` runs through the shell from the bundle root with `OKF_PROJECTION_OUT` naming an empty temporary directory, for at most 120 s, after which every process in its session is killed and what it wrote is read for at most 5 s more (a process that left the session is not waited for); each file it writes there is compared with the file of the same relative path in the projection's directory, and a file that differs, is absent there or, in a git work tree, is not tracked there (except in a `transient` projection, which is never committed) is drift. Nothing is recorded |
| `composed` | Prose a person or a model selected and wrote from its refs | A ref whose current SHA-256 (of the file's bytes; for a projection directory, of its `content.md`) differs from the recorded `sha256` |
| `recomputable` | `content.md` is a procedure over an external source; the render holds the dated values | Listed for a person to recompute by hand: rerun the procedure and propose the difference |

**`okf_projection.py`** (ADR-0031): `uv run <skills>/okf-standard/scripts/okf_projection.py [bundle] [--json] [--strict] [--run-render] [--record-hashes SLUG]`. Without a bundle it finds `knowledge/` upwards from the current directory. It reads every `projections/<slug>/projection.yaml` (hidden entries and plain files such as `.gitkeep` are ignored) and reports:

| Code | Level | When |
|---|---|---|
| `PROJ_NO_MANIFEST` | error | A directory in `projections/` without `projection.yaml` |
| `PROJ_BAD_YAML` | error | `projection.yaml` is not valid YAML, or not a mapping |
| `PROJ_MISSING_KEY` | error | A required key is missing (it is named), or a composed ref has no `sha256` (`refs[i].sha256`) |
| `PROJ_BAD_VALUE` | error | `lifecycle`, `nature` or `frozen` outside its values; a ref that is not a bundle path under `/base/` or `/projections/`; a `sha256` that is not 64 lowercase hex characters; a `versions` entry without `version` or `date` |
| `PROJ_REF_MISSING` | error | A ref whose path does not exist (a projection ref names an existing projection directory) |
| `PROJ_DEPENDENCY` | error | A ref that breaks the dependency rule |
| `PROJ_DRIFT` | warning | A composed ref or a rendered file that drifted, named |
| `PROJ_RENDER_FAILED` | error | A `render` that exits non-zero or times out, with the last lines of its output, secrets masked as `okf-lint` masks a validator's output |

Without `--run-render` nothing is executed: each rendered projection is listed under `not_checked`, with one notice, `render not run (use --run-render)`. An agent passes the flag only when a person asks, as for `--run-validators`. Recomputable projections are listed under `to_recompute`, frozen ones under `frozen`; both have their manifest checked. A manifest with errors is not checked for drift. `--json` gives `{ projections: [{slug, lifecycle, nature, frozen}], findings: [{code, level, slug, message}], not_checked, to_recompute, frozen, notices }`. The exit is 1 on any error, and on any warning with `--strict`; 2 when no bundle is found; else 0: drift asks for a refresh, not a fix. Rendering for real runs the same `render` with `OKF_PROJECTION_OUT` naming the projection's directory.

**`--record-hashes SLUG`**, after a person approves the refresh of a composed projection, writes each ref's current `sha256` into its `projection.yaml` in place: every other byte of the file stays as it was. It exits 2 and changes nothing, naming the reason, when the slug is not a projection, the projection is not composed or is frozen, its manifest has errors other than a `sha256` value, or a ref is not a one-line `{ path: ..., sha256: ... }` flow map.

### 2.2 Domain and operational bundles

A bundle is a **domain bundle** or an **operational bundle** (ADR-0039). A domain bundle holds knowledge that never closes: a domain, a system, a team, a doctrine. An operational bundle holds one unit of work, which opens, runs and closes: a request, an incident, a release and what it ships, an engagement. Which kinds of work exist is the organization's to name: the standard ships only the abstract kind `Operational Bundle`, and each bundle's Domain Profile declares its own kinds under `kinds` (§4.1). A bundle is open-ended or bounded by its kind, never by a key of its own.

**The definition lives in the domain bundle's `base/`; the instances live next to its layers.** The kind `Request` is declared in `base/profile.md`. How that work is done (its process, how a request closes, its terms and doctrine) is knowledge of the domain bundle: concepts in a directory of `base/` per kind, such as `base/requests/`, which `families` may declare. Each request is a bundle of its own in the directory its kind declares, never inside `base/`:

```
knowledge/                      domain bundle
├── index.md  log.md  project.md  fragments/  base/  projections/
├── base/
│   ├── profile.md              kinds: Request, Incident, Release
│   └── requests/               how requests are worked
├── requests/
│   ├── index.md                each instance with its state
│   └── req-0042/               kind: Request, state: open, parent: ../..
│       ├── index.md  log.md  project.md  conflict-log.md
│       └── fragments/  base/  projections/
└── releases/
    └── rel-2026-11/            kind: Release
        └── requests/
            └── req-0051/       a request the release ships; parent: ../..
```

An instance has the same layout at every depth: its `project.md` describes the unit of work, its `fragments/` record what happened in it, its `base/` holds what it knows, and it has its own `log.md` and, once it has a conflict, its own Conflict Log. An instance holds instances of the kinds its own kind `holds`, in their directories inside it. The directory of each kind has an `index.md` that lists its instances and their states.

**Root index of an operational bundle.** Every bundle's root `index.md` declares `okf_version` and `okf_profile` (§5.1). An operational bundle's also declares:

| Key | Required | Meaning |
|---|---|---|
| `kind` | Yes | A kind in force for it (below), by its id or an alias. A bundle without `kind` is a domain bundle; `kind: Domain Bundle` says so explicitly |
| `state` | Yes | `open`, `closed`, or a state its kind adds between them; `closed` is the only terminal state |
| `parent` | Yes, while it is in a tree | The bundle that holds it, as a path relative to the instance's directory (`../..`): the bundle it distills into. That bundle's kind (or, for a domain bundle, its Domain Profile) must allow this kind: a domain bundle holds every kind it declares, an operational bundle the kinds its kind `holds`. An extracted instance has none |
| `closed_at` | When `state: closed` | ISO 8601 with an explicit offset: when it closed |
| `depends_on` | No | Other bundles it refers to, each `{ bundle, repo?, ref? }`: `bundle` a path (relative to the instance's directory, or within `repo`), `repo` a repository name or URL, `ref` a tag, branch or commit. Declarative: lint checks its shape and shows it, and no tool resolves it |

A domain bundle declares no `state`, `parent` or `closed_at`.

```yaml
---
okf_version: "0.2"
okf_profile: "knowledge/3.0"
kind: Request
state: open
parent: ../..
depends_on:
  - { bundle: ../../incidents/inc-0412 }
  - { repo: payments-service, bundle: knowledge, ref: v2.3.0 }
---
```

**The Domain Profile in force for an instance** is the built-in profile, then the profile chain of the domain bundle at the top of its tree (every layer its `base/profile.md` `extends`, then that file), then the instance's own `base/profile.md` if it has one. An instance may add concept types, families and rules for its own concepts; it never declares `kinds`, which only a domain bundle does (`PROFILE_INVALID`).

**Closing.** A unit of work closes in three steps, each approved by a person:

1. **Distil its whole `base/` one level up.** `okf-distill` reads every concept of the instance's `base/` against the parent bundle and proposes one outcome for each: **promote** (lasting knowledge, added to the parent's `base/` or updating a concept there, citing the instance concept it came from), **conflict** (it contradicts the parent; opened in the parent's Conflict Log) or **stays** (it is about this unit of work only, and remains in the instance). The approved change set is kept as a **closing fragment in the parent's `fragments/`**, distilled, whose ledger has one row per concept of the instance's `base/`, linking the instance concept it read; each promoted concept cites that instance concept in its `sources`. Links run down only: the parent links into the instance, and the instance names its parent by path, as code, never by a link. One level at a time: a request a release ships distills into the release, and the release into the domain bundle when it closes.
2. **Leave no loose ends.** Each open conflict of the instance's Conflict Log and each open question of its `base/questions/` is resolved, or carried up into the parent as an open conflict or an open question that links back to it, and marked **`carried`** in the instance, a terminal value naming the parent's item by path: `question_status: carried` with `carried_to`, or State `carried` with the parent's row named in Resolution. A closing also stops while the instance has a pending fragment, holds an instance not yet closed, or its parent is closed. `okf_close.py` checks these and writes the closing once a person approves it.
3. **Close it.** `okf_close.py` writes `state: closed` and `closed_at` in the instance's root `index.md`; the agent adds a **Closing** entry in the instance's `log.md` and an **Update** entry in the parent's.

A closed instance is **frozen**: it stays where it is, lint still checks it, and nothing in it is edited; the audit (`okf_audit.py`, the audit mode of `okf-review`) looks inside each instance and reports any concept whose `generated.at` is later than its `closed_at`, and lint does not read git for it. Or it is **extracted**: moved to its own repository, without `parent`, its `base/profile.md` pinning the definition of its kind with `extends: <path>@<commit>`.

**What lint checks** (rule 16 of §7). Linting a bundle also checks every instance in the directories of the kinds it may hold, at any depth, each as a bundle of its own: its findings name the instance's path, and the summary counts them apart. `--no-nested` skips the instances, with one notice per kind directory. Linting an instance's directory alone reads its parents for the Domain Profile in force.

| Code | Level | Breach |
|---|---|---|
| `KIND_UNKNOWN` | error | `kind` names no kind in force, or a bundle with `kind` has no `okf_version` |
| `KIND_NOT_HELD` | error | The parent does not allow this kind, or an instance is in a directory other than its kind's |
| `BAD_PARENT` | error | An instance in a tree without `parent`, or a `parent` that is not the bundle holding it; a domain bundle with `parent` |
| `BAD_STATE` | error | A missing `state` on an operational bundle, a value its kind does not allow, or a `state` on a domain bundle |
| `BAD_CLOSED_AT` | error | `state: closed` without `closed_at`, a `closed_at` that is not ISO 8601 with an offset, or a `closed_at` on an open bundle |
| `CLOSED_LOOSE_END` | error | A closed instance whose Conflict Log has an open or proposed conflict, or that has an open question or a pending fragment |
| `BAD_DEPENDS_ON` | warning | A `depends_on` that is not a list of maps, each with a text `bundle` and only `repo` and `ref` beside it |

## 3. Concept document

Every non-reserved `.md` file is a **concept**: YAML frontmatter + markdown body.

### 3.1 Frontmatter

```yaml
---
type: Runbook                              # REQUIRED
title: Freshness alert response            # recommended
description: Steps to triage a freshness alert on the orders pipeline.  # recommended, one sentence
resource: https://grafana.acme/d/abc       # URI of the underlying asset, if there is one
tags: [oncall, incidents, orders]          # recommended
status: stable                             # draft | stable | deprecated (absent ⇒ stable)
stale_after: 2027-06-30T00:00:00Z          # absolute instant after which the content is stale
generated: { by: human:jisequilla, at: 2026-10-30T16:00:00Z }
verified:
  - { by: human:jisequilla, at: 2026-10-30T16:00:00Z }
sources:
  - id: sre-handbook
    resource: https://wiki.acme/sre/handbook
    title: SRE handbook
    author: team:sre
    last_modified: 2026-09-01T00:00:00Z
---
```

| Field | Required | Profile rule |
|---|---|---|
| `type` | **Yes** | Use the vocabulary in §4, or a type the bundle's Domain Profile declares (§4.1). New types are allowed if they are self-explanatory. |
| `title` | Recommended | If missing, the consumer derives it from the file name. |
| `description` | Recommended | One sentence. It is what appears in `index.md`. |
| `resource` | If applicable | Canonical URI of the asset (repo, dashboard, table, endpoint). |
| `tags` | Recommended | YAML list, lowercase, kebab-case. |
| `status` | Recommended | `draft` on creation; `stable` after review; `deprecated` is never deleted, it links to its replacement. |
| `stale_after` | Recommended in runbooks, metrics, policies | ISO 8601 with an explicit offset. |
| `generated` | **Required in the profile** | `{ by: <actor>, at: <ISO 8601> }`. Who/what wrote the current content. |
| `verified` | Recommended | List of `{ by, at }`. A single map is read as a one-item list. A `human:` entry is written by that person, or by an agent from the person's recorded answer (§6). |
| `sources` | Recommended if the content derives from something | Each entry with a required `resource`; `id` if the body cites it with a `[^id]` footnote. |

**Actor convention (§7 of the spec):** `human:<id>` for people, `process:<id>` for automated processes, `<producer>/<version>` for agents (e.g. `okf-builder/claude-fable-5-1`). The `human:` prefix is what raises the trust level to *human-reviewed*.

**Derived trust levels:** no `verified` ⇒ *unverified*; `verified` only by non-humans ⇒ *machine-confirmed*; any `human:` ⇒ *human-reviewed*.

### 3.2 Body

Structured markdown (headings, lists, tables, code blocks) before free prose. Headings with a conventional meaning:

| Heading | Use |
|---|---|
| `# Schema` | Columns/fields of a data asset (a table with Column / Type / Description). |
| `# Examples` | Usage examples in code blocks. |
| `# Computation` | A single code block with the sanctioned computation (only `type: Attested Computation`). |

The headings of the other templates (§5) are recommendations of the profile, not of the spec.

### 3.3 Links

- Recommended form: **bundle-absolute**, starting with `/`: `[orders](/base/data/orders.md)`.
- Relative allowed: `[neighbour](./other.md)`.
- A broken link is **not** a conformance error: it represents knowledge not yet written. `okf-lint` reports it as a warning.
- Per-claim attribution: a footnote whose label is a `sources[].id`: `...is partitioned by day.[^ga4-schema]`.

## 4. Profile type vocabulary

| `type` | Usual directory | Description |
|---|---|---|
| `Project` | root | Project overview. Exactly one per bundle (`project.md`). |
| `Architecture View` | `base/architecture/` | Context, containers, components, deployment, principles. |
| `Architecture Decision` | `base/decisions/` | ADR. Extra fields: `adr_id`, `decision_status` (proposed/accepted/superseded/rejected), `supersedes`, `superseded_by`. |
| `Term` / `Glossary` | `base/domain/` | A business term, or the aggregated glossary. |
| `System` | `base/systems/` | Service, module, job, deployable component. Extra fields: `owner` (who owns it: a team or a person, as a string), `repo`, `runtime`. |
| `API` | `base/apis/` | Contract; `resource` points to the OpenAPI/Proto/AsyncAPI. Extra fields: `owner` (who owns it: a team or a person, as a string). |
| `Dataset` | `base/data/` | Data asset. Body with `# Schema` and `# Joins`. |
| `Table` | `base/data/` | Data asset. Extra fields: `owner` (who owns it: a team or a person, as a string). Body with `# Schema` and `# Joins`. |
| `Metric` | `base/metrics/` | Business definition; links to its `Attested Computation`. Extra fields: `owner` (who owns it: a team or a person, as a string). |
| `Attested Computation` | `base/computations/` | Name fixed by the spec (§10). Requires `runtime`. |
| `Runbook` | `base/runbooks/` | Operational procedure: Trigger, Diagnosis, Steps, Rollback, Escalation. Extra fields: `owner` (who owns it: a team or a person, as a string). |
| `Playbook` | `base/playbooks/` | Team/business procedure. Extra fields: `owner` (who owns it: a team or a person, as a string). |
| `Policy` | `base/policies/` | Rule or standard; usually carries `stale_after` and a human `verified`. Extra fields: `owner` (who owns it: a team or a person, as a string). |
| `Reference` | `base/references/` | Mirrored external material or execution instructions. |
| `Knowledge Fragment` | `fragments/` | Record of an event (meeting, chat, slides, transcript), named `YYYY-MM-DD-slug.md` with the date of the event. Extra fields: `occurred_at` (when it happened: `YYYY-MM-DD` or ISO 8601 with an offset), `origin` (where it happened), `participants` (list of actors, §3.1), `distillation_status` (`pending` / `distilled` / `conflict`), and optionally `material` (a list of `{ path, sha256 }`: each file the record was taken from, `path` a bundle path `/...` or one relative to the bundle root, never to the fragment's directory, and `sha256` the 64-hex SHA-256 of the file as kept, the redacted file if it was redacted) and `repository` (`{ url, commit }`: the repository the record was taken from, at its full 40-hex commit), ADR-0029. Body: `# Record` (immutable after capture) and `# Distillation`, whose table (`Item | Kind | Outcome | Concept`, ADR-0015) is the ledger of a distilled fragment: one row per part of the record, its Concept a link (or links) to the concept(s) it went into, `tracker` (an action item filed in the team's tracker) or `no concept (<reason>)`, so nothing in the record is left unaccounted for; bundles written in Spanish may title them «Contenido capturado» and «Destilado en». After capture only `distillation_status` and `# Distillation` change, except that a missing `occurred_at`, `origin` or `participants` may be backfilled once (§6); `material` and `repository` are written at capture only. |
| `Open Question` | `base/questions/` | What the team does not know yet, named `<kebab-slug>.md` (no ID). Extra fields: `owner` (an actor, §3.1, required), `question_status` (`open` / `answered` / `dropped` / `carried`), `asked_in` (the bundle path of the fragment where it arose, `/fragments/<file>`; absent when it arose outside any fragment, whose origin `sources` then cites), and optionally `blocks` (list of the concepts it holds up), `review_on` (a date `YYYY-MM-DD`), `answered_by` (the concept that answers it) and `carried_to` (with `carried`: the parent bundle's item it was carried up into, a path relative to the instance root, as text). Body: `# Question`, `# Why it matters`, `# What is known` and `# Answer`. Never deleted: an answered one links its answer. `status` (`draft` / `stable` / `deprecated`) is independent of `question_status`: answering, dropping or carrying a question does not deprecate it. |
| `Conflict Log` | root (`conflict-log.md`) | The bundle's conflict register. Zero or one per bundle; created with the first conflict. Body: a table with the columns ID (`C-NNN`), source fragment, description, kind, resolution, state (`open` / `proposed` / `resolved` / `dismissed` / `carried`, the last naming the parent bundle's row in the resolution) and who decided. |
| `Domain Profile` | `base/profile.md` | The bundle's taxonomy, on top of the built-in Domain Profile (§4.1). Zero or one per bundle, only at `base/profile.md`. Keys: `extends`: shared profiles it builds on, by reference, a bundle path (`/base/...`) or a repository path pinned to a commit (`<path>@<commit>`), never copied · `types`: each local type, with the type it `extends`, `description` and `fields` · `fields`: per type, each field's `type` (one of eleven), `of`, `values` or `keys`, `required`, `level` (`error` or `warn`), `note` · `families`: per directory under `base/`, the types allowed there and its own `required`, `fixed`, `forbidden` · `forbidden`: keys that must not appear, with reason and level · `fixed`: keys whose value is fixed, with value and level · `by_type`: `required`, `fixed` or `forbidden` for one type · `rules`: named conditions across fields (`when`, `require`, `level`) · `validator`: types or families another tool validates, and the command · `questions`: the questions the bundle answers, each mapped to a `Type.field` or a concept · `aliases`: optional, local names for types, fields and values. An extension only adds. Body: what the bundle holds and the justification of each type and field, with sources. |
| `Log` | — | Only for `log.md` if frontmatter is added to it (optional, tolerated by consumers). |

Types are not registered centrally; consumers must tolerate unknown types. A bundle declares its own types in its Domain Profile (§4.1).

### 4.1 Domain Profile

**Two meanings of "profile".** In this document *the profile*, alone, is `knowledge/3.0`: the layout, the `okf_profile` key, the "profile outdated" notice, `okf-lint --no-profile`, and the `PROFILE_*` codes that are not in the table of codes below (`PROFILE_NO_GENERATED`, `PROFILE_OUTSIDE_LAYER` and the like). A **Domain Profile** is the taxonomy a bundle's concepts are checked against (ADR-0026). *The Domain Profile in force* for a concept is what every layer declares for its type and its directory, and the codes in the table below are about it.

**The built-in Domain Profile.** The types of the table above are a built-in Domain Profile, shipped with the `okf-standard` skill at `<skills>/okf-standard/profiles/knowledge-3.0.md` and versioned with the plugin. It is a `Domain Profile` concept: its frontmatter is the data and its body justifies each type and field from this standard. It declares each type of §4 with its fields, levels and usual directory; `Domain Profile` is declared by name only, because its keys nest maps inside maps, deeper than the one-level `map` field type describes, and lint checks them itself against this section (`PROFILE_INVALID`). Each requirement may carry the `code` lint reports, so the per-field checks of a Knowledge Fragment and an Open Question keep their codes and levels: `FRAGMENT_NO_FIELD` and `QUESTION_NO_FIELD` (warnings), `BAD_DISTILLATION_STATUS` and `BAD_QUESTION_STATUS` (errors), `BAD_ACTOR`, `BAD_ISO`, `BAD_MATERIAL` and `BAD_REPOSITORY` (warnings) for the fields it declares, and its rules keep theirs: `QUESTION_NO_ANSWER` and `QUESTION_NO_CARRIED_TO` (warnings); the actor and timestamp checks of `generated`, `verified`, `stale_after`, `timestamp` and `sources[].last_modified` stay with the spec-level checks. It declares no `families`: the usual directory of a type is a default, not a rule. It also declares the abstract kind `Operational Bundle`, the one every bundle's kinds extend (§2.2). It is the first layer of every bundle's Domain Profile, and a bundle without `base/profile.md` is checked against it alone. Its content changes only with this standard.

**Where a Domain Profile applies.** A bundle's own Domain Profile is read only in a `knowledge/3.0` bundle and only at `base/profile.md`. A `profile.md` in a `knowledge/2.0` bundle is ignored with a notice to migrate, and the built-in one still applies. A shared profile that `base/profile.md` reaches through `extends` by bundle paths (`/base/shared/profile.md`, directly or through another profile reached that way) is read from the working tree as a layer and is not misplaced. In a `knowledge/3.0` bundle, any other concept of type `Domain Profile` is `PROFILE_MISPLACED`; in a `knowledge/2.0` bundle it is ignored like `profile.md`. `okf-lint --no-profile` validates the OKF spec only: it turns off the `knowledge/3.0` profile and every Domain Profile with it, the built-in one included, so neither the Knowledge Fragment and Open Question checks nor any code of the table below is reported, and `base/profile.md` is read as an ordinary concept.

**Keys.**

| Key | Form | Meaning |
|---|---|---|
| `extends` | list of references | Shared profiles this one builds on, merged in order: a bundle path (`/base/shared/profile.md`), or a repository path pinned to a commit (`profiles/acme.md@3f2a9c1`), read with `git show <commit>:<path>` from the repository that holds the bundle. Never copied. A URL is not read: it is `PROFILE_UNREADABLE`, naming the missing support |
| `types` | map: type id → definition | Each local type: `extends` (a type of the built-in profile or of an extended profile), `description`, `fields` |
| `fields` | map: field id → definition, per type | `type`: `string`, `integer`, `boolean`, `date` (`YYYY-MM-DD`), `datetime` (ISO 8601 with an explicit offset), `date_or_datetime` (either), `actor` (the actor convention, §3.1), `list` (with `of`, the field type of each item), `enum` (with `values`), `path` (a bundle path, starting with `/`), `map` (with `keys`; a `list` with `of: map` takes `keys` too). `keys`: map key → definition, each key of a scalar type (any type but `list` and `map`: one level deep) with `values` for an enum, `required` (`true` or `false`) and `note`, and no `level` or `code` of its own: a value that is not a map, a missing required key and a key of another type are breaches of the field, at its level and under its code (`PROFILE_FIELD_TYPE` without one), and a key the declaration does not name is not reported; an empty map counts as missing, so on an optional field it is not reported, and an empty item of a `list` of `map` is one breach naming the item. `required`: `true`, or `{ level, code }` when a missing field has its own level or code. `level`: `error` (the default) or `warn`, the level of every breach of the field. `code`: optional, the code lint reports instead of the generic one. `note`: what the field holds |
| `kinds` | map: kind id → definition | Domain bundles only. Each operational kind (§2.2): `extends` (`Operational Bundle` or a kind of an extended profile), `description` (what one unit of this work is), `directory` (where its instances live, relative to the bundle that holds them, ending in `/`: `requests/`; never a reserved file or a layer), `states` (states added between `open` and `closed`, in order), `holds` (the kinds an instance of it may hold). A kind inherits the `states` and `holds` of the kind it extends |
| `families` | map: directory → schema | Per directory under `base/`, written as its bundle path with both slashes (`/base/clients/`): `types` (the types allowed there; absent ⇒ any type), and `required`, `fixed` and `forbidden` that apply only there. A family covers its directory and every subdirectory; where families nest, each one applies. `/base/` itself is not a family, so `base/profile.md` is in none. A directory no family covers allows any type |
| `forbidden` | map: key → `{ reason, level }` | Keys that must not appear in any concept |
| `fixed` | map: key → `{ value, level }` | Keys whose value is fixed: where the key is present it holds exactly that value. To require the key as well, list it in `required` |
| `by_type` | map: type id → `{ required, fixed, forbidden, values }` | Requirements for one type and the local types that extend it; `values` adds values to an enum field the type inherits |
| `rules` | list | Named conditions across fields, few and declarative: `{ name, when: { field: value }, require: [fields], level }` |
| `validator` | list | `{ name, types, families, command }`: types or families validated by another tool, and the command that does it |
| `questions` | list | `{ question, field: Type.field }` or `{ question, concept: /base/... }`: the questions the bundle answers. A question mapped to a field is answered from the frontmatter: a concept of that type without the field is the gap. A `concept` that does not exist is a broken link (a warning, §3.3) |
| `aliases` | map | Optional. `types` (`Fragmento: Knowledge Fragment`), `fields` (`fecha: occurred_at`) and `values` (`{ from: { ingerido: true }, to: { distillation_status: distilled } }`): local names for declared ones |

`forbidden`, `fixed` and `rules` entries may carry a `code` too, and their `level` is `error` when absent. A key that a `required` or `fixed` names counts as declared for the concepts that requirement applies to.

```yaml
extends: [/base/shared/profile.md, profiles/acme.md@3f2a9c1]
types:
  Client Meeting:
    extends: Knowledge Fragment
    description: A meeting with a client, recorded as it happened
    fields:
      client: { type: string, level: warn, note: "The client's name as the contract writes it" }
      contract: { type: path, note: The concept of the contract the meeting is about }
kinds:
  Request: { extends: Operational Bundle, description: A change a client asks for, directory: requests/, states: [in-review] }
  Incident: { extends: Operational Bundle, description: An outage and what it taught, directory: incidents/ }
  Release: { extends: Operational Bundle, description: A release and what it ships, directory: releases/, holds: [Request, Incident] }
families:
  /base/clients/:
    types: [Term, System, Architecture Decision, Open Question]
    required: [tags]
forbidden:
  internal_notes: { reason: Internal notes stay out of the bundle, level: error }
fixed:
  okf_lang: { value: en, level: warn }
by_type:
  Policy: { required: [stale_after] }
rules:
  - { name: distilled-client-meeting-names-client, when: { type: Client Meeting, distillation_status: distilled }, require: [client], level: warn }
validator:
  - { name: openapi, types: [API], command: "npx @redocly/cli lint" }
questions:
  - { question: "Who owns each system?", field: System.owner }
  - { question: "How is the product deployed?", concept: /base/architecture/deployment.md }
aliases:
  types: { Reunión con cliente: Client Meeting }
  fields: { cliente: client }
  values: [{ from: { ingerido: true }, to: { distillation_status: distilled } }]
```

**Composition.** The rules of ADR-0026, decision 4:

- an extension only adds: a type, field, enum value or rule defined higher up is never redefined or removed, and a level is never lowered;
- the same id (type, kind, field, family or rule) from two sources is a structural error, not an override;
- layers merge from general to specific: the built-in profile, then each extended profile in order, then the bundle's own declarations, then `families`, then `by_type`. A layer's `families` and `by_type` come after the declarations of every layer and before the next layer's `families`, so a `by_type` entry is narrower than the families of its own and earlier layers, and a family is narrower than the `by_type` of earlier layers. A `by_type` key may be a type alias; the entries one layer writes for one type, under its name and its aliases, are one entry and agree;
- a reference that cannot be read is an error. Lint reads references locally, never over the network: a bundle path from the bundle, `<path>@<commit>` from the bundle's own repository. A URL is not read; it is an error that names the missing support.

A lower layer may add a type, a kind, a field to a type it declares, a rule, a family or a requirement: make an optional field required, raise `warn` to `error`, forbid or fix a key. It may also add values to an enum it inherits, and only through `by_type`: `by_type: { Knowledge Fragment: { values: { distillation_status: [archived] } } }` adds `archived` for that type and the local types that extend it. It never changes a field's type, never removes or renames a value, never makes a required field optional and never lowers a level. A bundle adds a field to a standard or inherited type only through a local type that `extends` it (`Client Meeting` above), never by declaring that type again. A value a bundle adds is new to the skills: they read it from `--profiles`, and one they cannot act on is raised to a person.

The two structural errors differ by where the second declaration comes from. **`PROFILE_DUPLICATE_ID`**: the same id declared in `types`, `kinds`, `families`, `rules` or `aliases` by two sources, whatever the layers and even when both definitions are equal: two extended profiles that declare the same type, a bundle that declares `Knowledge Fragment` again in its own `types`, a rule name or a family directory declared twice, an alias named like a declared id. **`PROFILE_REDEFINED`**: a change to something a higher layer declares, made through the keys meant for adding: a local type whose `fields` declares again a field of the type it extends; a `by_type` or family entry that lowers a level, makes a required field optional, changes a field's type or a map field's `keys`, or removes an enum value. A map field composes strictly: no lower layer changes its `keys`.

What is in force for a local type includes everything in force for the type it extends, its `by_type` entry included, and a family that allows a type allows the local types that extend it.

**What lint checks.** `okf-lint` validates each concept against the Domain Profile in force for its type and its directory, and reports each breach at its declared level. A requirement with its own `code` is reported under that code in every `knowledge/3.0` bundle. In a bundle that has a `base/profile.md`, every other item in force is checked too, the built-in profile's included, under the generic codes below; in a bundle without one, the built-in profile's items without a code are listed by `--profiles` and not reported. A concept whose type no layer declares is tolerated (§4): it is checked against `forbidden`, `fixed`, `rules` and the `types` of the families that cover it, and never warned about for its type. In a bundle that has a `base/profile.md`, a key no layer declares for the concept (the spec's keys, the keys of §3.1, the fields declared for its type and the types it extends, and the keys a `required` or `fixed` names for it) is a warning; in a bundle without one, undeclared keys are not reported. Lint and the skills resolve aliases first, so a local name gets the checks of the type, field or value it stands for. `okf-lint --profiles` lists what is in force for a path and which layer declared each item.

**Validators run only on request.** `okf-lint` runs a profile's `validator` commands only with `--run-validators`, from the bundle root with the paths of the matching concepts as arguments, and reports each failure as an error (`PROFILE_VALIDATOR`) with secrets masked. Without the flag it prints the notice "validator <name> not run (use --run-validators)" for each one. A bundle's content never runs a command by default, and the skills ask the person before passing the flag.

**What stays in code** (ADR-0026, decision 6). Checks across concepts or over a body: at most one Conflict Log per bundle; the layer rule of a 3.0 bundle; an open question past its `review_on`; the single fence of an Attested Computation; the structure of `index.md` and `log.md`. They apply to a local type through the standard type it extends.

**Codes.**

| Code | Level | Breach |
|---|---|---|
| `PROFILE_INVALID` | error | The Domain Profile does not follow the schema of this section |
| `PROFILE_DUPLICATE_ID` | error | A type, kind, field, family, rule or alias id declared by two sources |
| `PROFILE_REDEFINED` | error | An extension changes or removes something defined higher up, or lowers a level |
| `PROFILE_UNREADABLE` | error | A reference in `extends` that cannot be read locally, a URL included |
| `PROFILE_MISPLACED` | error | A concept of type `Domain Profile` anywhere other than `base/profile.md` and the profiles it reaches through `extends` by bundle paths |
| `PROFILE_REQUIRED` | declared | A required field is missing |
| `PROFILE_ENUM` | declared | A value outside its enum's `values` |
| `PROFILE_FORBIDDEN` | declared | A forbidden key is present |
| `PROFILE_FIXED` | declared | A fixed key holds another value |
| `PROFILE_RULE` | declared | A rule's `when` holds and a field it `require`s is missing |
| `PROFILE_TYPE_NOT_ALLOWED` | declared | A concept whose type a family that covers it does not allow |
| `PROFILE_FIELD_TYPE` | declared | A value of another type than its field declares |
| `PROFILE_VALIDATOR` | error | A validator run with `--run-validators` failed |
| `PROFILE_UNKNOWN_KEY` | warning | A key no layer declares, in a bundle that has a `base/profile.md` |

"Declared" is the requirement's `level`, `error` when absent. A requirement with its own `code` is reported under that code: the built-in profile keeps `FRAGMENT_NO_FIELD`, `QUESTION_NO_FIELD`, `BAD_DISTILLATION_STATUS`, `BAD_QUESTION_STATUS`, `BAD_ACTOR` and `BAD_ISO`, and declares `BAD_MATERIAL` and `BAD_REPOSITORY`.

## 5. Reserved files

### 5.1 `index.md`

- One per directory. No frontmatter, **except** the root one, which carries `okf_version: "0.2"` and, in this profile, `okf_profile: "knowledge/3.0"`; the root `index.md` of an operational bundle also carries `kind`, `state`, `parent`, `closed_at` and `depends_on` (§2.2). The root of each bundle is its own root: an instance's `index.md` is a root `index.md`.
- Body: sections with a `#` heading and a list of links `* [Title](path) - description`. The description is copied from the concept's `description`.
- The root `index.md` lists the root concepts, the three layers and each kind's directory as subdirectories; a kind's directory lists its instances, each with its state; `base/index.md` lists the typed directories and, when the bundle has one, `base/profile.md`. `okf-index` regenerates it; hand-written sections starting with `# Notes` (or `# Notas`) are kept.

```markdown
---
okf_version: "0.2"
okf_profile: "knowledge/3.0"
---

# Project

* [Project overview](project.md) - Purpose, scope and key links of the project.

# Subdirectories

* [fragments](fragments/index.md) - Records of events, distilled into the base.
* [base](base/index.md) - The project's knowledge, in typed directories.
```

A kind's directory, here `requests/`: the kind's `description` from the Domain Profile as its blockquote, then one entry per instance, the instance's directory name, its `project.md` description and its `state`:

```markdown
> A customer request

# Instances

* [req-1](req-1/index.md) - Refund flow for the EU stores. _(state: open)_
* [req-2](req-2/index.md) - Loyalty points on returns. _(state: closed)_
```

### 5.2 `log.md`

- At least at the root. A flat list grouped by ISO date `YYYY-MM-DD`, **most recent first**.
- Each entry starts with a bold word: `**Creation**`, `**Update**`, `**Verification**`, `**Deprecation**`, `**Initialization**`, `**Migration**` (an OKF version or profile migration), `**Conflict**` (opening or resolving a conflict of the Conflict Log), `**Closing**` (an operational bundle closes, §2.2).

```markdown
# Bundle history

## 2026-10-30
* **Initialization**: `knowledge/` structure created with the knowledge/3.0 profile.
```

## 6. Knowledge lifecycle

| Event | Action | Frontmatter |
|---|---|---|
| Create a concept | `okf-capture` with a template | `status: draft`, `generated` with the actor who writes it |
| Human review | A person reviews the concept as it stands at a named version, and writes `verified` by hand or gives the agent a recorded answer, in a structured question or on a review page only that person can answer on, naming each concept by bundle path, repository commit and `generated.at` (never a chat reply, never for someone else); the agent keeps the question and the answer, or the page's stored answers, verbatim as a `Knowledge Fragment`. A concept edited afterwards is asked again | `status: stable`, add `verified: { by: human:<id>, at }` (`at`: the time of the answer); a **Verification** entry in `log.md`, linking the fragment when an agent wrote it |
| Content change | Edit | Update `generated.at`; `verified` is **not** touched (it can end up older than `generated.at`; that gap is information) |
| Reconfirm without changes | Periodic review | Add a new entry to `verified` |
| Staleness | `now >= stale_after` | `okf-lint` warns; review and renew `stale_after` or deprecate |
| Capture a fragment | `okf-fragment` records an event in `fragments/` | `type: Knowledge Fragment`, `status: draft`, `distillation_status: pending`, `generated` |
| Backfill a fragment | `okf-fragment` fills a missing `occurred_at`, `origin` or `participants` with a value read from `# Record` or from an original its `sources` cite, never inferred; a person approves it, the mapping of names to actors included. A value already written is never changed: a wrong one means the fragment is deprecated and replaced | Only the absent field is added; `# Record`, `generated` and every other key stay as they are; an **Update** entry in `log.md` names the fragments, the fields and who approved them. A fragment whose record does not show the value keeps the field absent |
| Distill a fragment | `okf-distill` routes each item by the table in §2 and proposes a change set (additions, confirmations, updates, refutations, conflicts); action items are listed for the team's tracker and never written to `base/`; a refutation deprecates an outdated concept and links its replacement without opening a conflict, and anything disputed is a conflict; a person approves it before anything is applied | Touched concepts cite the fragment in `sources`; the fragment gets `distillation_status: distilled` (or `conflict` while one of its conflicts is open). Distillation never sets `verified` |
| Resolve a conflict | A person decides: the knowledge changed (new ADR that supersedes, an **Update** citing the fragment, or a deprecation as in a refutation) or it was a misunderstanding (dismissed with the reason) | The row of the Conflict Log changes its state and records who decided; the fragment returns to `distilled` when no conflict of it is open; a **Conflict** entry in `log.md` |
| Open a question | `okf-capture` or `okf-distill` writes an `Open Question` in `base/questions/` with the template | `type: Open Question`, `status: draft`, `owner`, `question_status: open`, `asked_in` (or the origin in `sources`), `generated`; a **Creation** entry in `log.md` |
| Answer a question | The concept that holds the answer is created or updated and cites the question in `sources` (`resource: /base/questions/<slug>.md`); the question's `# Answer` summarizes it and links it | `question_status: answered`, `answered_by` with the answer's bundle path, `generated.at` updated; `status` unchanged; an **Update** entry in `log.md` |
| Drop a question | A person decides the question no longer needs an answer; the reason goes under `# Answer` | `question_status: dropped`, `generated.at` updated; `status` unchanged; the question is never deleted; an **Update** entry in `log.md` |
| Carry up a question or conflict | While an operational bundle closes (§2.2), a person decides an open question or open conflict of the instance lives on in its parent; `okf_close.py` writes it | In the parent: an open question or an open Conflict Log row that links back to the instance's item. In the instance: `question_status: carried` with `carried_to`, or State `carried` with the parent's row named in Resolution, each the parent's item by path, as code; `generated.at` updated; the item is never deleted |
| Supersession | New concept | Old one: `status: deprecated` + a link to the new one. Never delete: that breaks the graph and the history |
| Declare or change the profile | `okf-capture` writes `base/profile.md` with the `domain-profile.md` template, and `okf-distill` proposes a change to it as an item of a change set; either applies a change only after a person approves it. It is a concept like any other, edited in place. Friction with the Domain Profile (a concept lint rejects, a value an enum lacks) is raised to a person, never resolved by relaxing an enum, a level or a rule to silence lint | `type: Domain Profile`, `status: draft`, `generated`, `sources`; a person may verify it; a change edits `base/profile.md` in place, with a new `generated.at` and an **Update** entry in `log.md`, and git keeps the earlier versions; a bundle that drops its profile sets `status: deprecated`, and lint then applies the built-in profile alone; a **Creation** entry when it is first written |
| A new type emerges | A concept first fits an existing type; if one almost fits, a new type is proposed to a person; if none fits, the bundle declares a local one in `base/profile.md`, justified in its body. When a second bundle wants a local type, it is promoted to a shared profile by a pull request to that profile's repository, and the bundles `extends` it | The new type in `types`, with `extends`, `description` and `fields`; `generated.at` updated; an **Update** entry in `log.md` |
| Audit the bundle | The audit mode of `okf-review`, optionally since a reference point the person names (a commit, a tag, or a date read as the last commit before it): `okf-lint`'s findings and metrics grouped by what a person must do; `okf_audit.py`'s git facts (read-only git), the concepts deleted or renamed since then (lint's exclusions applied; a rename not yet added to git found by identical content) that nothing records: a deletion needs a deprecation at the reference point or a **Deprecation** entry, or one saying it was deprecated, removed or superseded, added since to the root `log.md` or its directory's, and a rename an entry added since naming both paths; the audit's own entries never count (`DELETED_UNRECORDED`, `RENAMED_UNRECORDED`), skipped with a notice without a reference point or outside git; and the findings that need judgment (unwritten terms and systems, missing sections, unfootnoted claims, `sources` no footnote cites, contradictions outside the Conflict Log, links to retired targets, parts of a free-text record no ledger row accounts for). A person decides each finding: fix now, open question, conflict, accept as is or tracker; nothing changes before that, and a finding inside an Architecture Decision is never fixed by editing its body, except a committed secret, removed and rotated since that does not change the decision | Only what the person decided to fix changes, under that event's rules; one **Update** entry in `log.md` names the audit and its reference point and lists the findings accepted as is, which a later audit at the same reference point leaves out |
| Open a unit of work | `okf-init` creates an instance of a kind in the kind's directory of the bundle that holds it (§2.2) | Its root `index.md` with `kind`, `state: open`, `parent`; `log.md` with an **Initialization** entry, `project.md`, the three layers; an **Update** entry in the parent's `log.md` |
| Close a unit of work | `okf-distill` distills the instance's whole `base/` into its parent (promote, conflict or stays), its open conflicts and questions are resolved or carried up, and a person approves each step; `okf_close.py` checks that it may close and writes the closing (§2.2) | The closing fragment, distilled, in the parent's `fragments/`; `state: closed`, `closed_at`, the `carried` values; a **Closing** entry in the instance's `log.md`, an **Update** entry in the parent's |
| Extract a closed unit of work | It moves to its own repository | `parent` removed; its `base/profile.md` `extends` the definition of its kind at `<path>@<commit>`; an **Update** entry in both bundles' `log.md` |
| Any of the above | Log | An entry in the `log.md` of the affected directory and/or the root |

## 7. Conformance

A `knowledge/` bundle is **OKF v0.2 conformant** if:

1. Every non-reserved `.md` has a parseable YAML frontmatter block (a non-OKF directory, below, is not checked).
2. Every frontmatter has a non-empty `type`.
3. `index.md` and `log.md`, when they exist, follow §5.

It is **conformant with this profile** if, in addition:

4. `knowledge/index.md` (with `okf_version`), `knowledge/log.md` and `knowledge/project.md` (`type: Project`) exist, and so do the same three files at the root of each operational bundle.
5. Every concept carries `generated.by` following the actor convention.
6. Timestamps are ISO 8601 with an explicit offset; the exceptions are a Knowledge Fragment's `occurred_at` and an Open Question's `review_on`, which also accept a date `YYYY-MM-DD`.
7. `status`, if present, is `draft | stable | deprecated`.
8. `Attested Computation` concepts carry `runtime` and either `computation` or a `# Computation` block with a single fence.
9. File names are ASCII kebab-case.
10. A Knowledge Fragment's `distillation_status`, if present, is `pending | distilled | conflict`.
11. At most one concept per bundle has `type: Conflict Log`.
12. In a `knowledge/3.0` bundle, concepts live only in `base/` (at any depth) or `fragments/`; the root holds no concept other than `project.md` and `conflict-log.md`, and no directory other than the layers and the directories of the kinds the bundle may hold. `projections/` is not checked.
13. An Open Question's `question_status`, if present, is `open | answered | dropped | carried`.
14. In a `knowledge/3.0` bundle, the Domain Profile is well formed (§4.1): it follows the schema (`PROFILE_INVALID`), no id is declared by two sources (`PROFILE_DUPLICATE_ID`), no extension redefines or removes what a higher layer defines or lowers a level (`PROFILE_REDEFINED`), every reference in `extends` can be read locally (`PROFILE_UNREADABLE`), and `type: Domain Profile` appears only at `base/profile.md` and in the profiles it reaches through `extends` by bundle paths (`PROFILE_MISPLACED`).
15. Every concept meets the Domain Profile in force for its type and its directory (§4.1), at each requirement's declared level: required fields (`PROFILE_REQUIRED`), enums (`PROFILE_ENUM`), forbidden keys (`PROFILE_FORBIDDEN`), fixed keys (`PROFILE_FIXED`), rules (`PROFILE_RULE`), a type every family that covers it allows (`PROFILE_TYPE_NOT_ALLOWED`) and values of each field's declared type (`PROFILE_FIELD_TYPE`). Rules 10 and 13 and the Knowledge Fragment and Open Question warnings below are requirements of the built-in Domain Profile, reported under their own codes; its requirements without a code apply only in a bundle that has a `base/profile.md`.
16. Every operational bundle (§2.2) declares a `kind` in force (`KIND_UNKNOWN`) that its parent allows, in its kind's directory (`KIND_NOT_HELD`); its `parent` is the bundle that holds it (`BAD_PARENT`); its `state` is one its kind allows (`BAD_STATE`); `closed_at` is present exactly when it is closed (`BAD_CLOSED_AT`); a closed one holds no open or proposed conflict, no open question and no pending fragment (`CLOSED_LOOSE_END`); and its `depends_on` has the declared shape (`BAD_DEPENDS_ON`, a warning). Each instance meets rules 1–15 as a bundle of its own.

`okf-lint` separates **errors** (1–5, 7, 8, 10–14, the breaches of 15 at level `error`, and 16 but `BAD_DEPENDS_ON`) from **warnings** (6, 9, the breaches of 15 at level `warn`, `BAD_DEPENDS_ON`, broken links, expired `stale_after`, concepts without `description`, out-of-date `index.md`, Knowledge Fragments missing `occurred_at`, `origin`, `participants` or `distillation_status` (`FRAGMENT_NO_FIELD`), `participants` not following the actor convention (`BAD_ACTOR`), `occurred_at` that is neither a date nor an ISO 8601 datetime with an offset (`BAD_ISO`), a `material` entry that is not a `{ path, sha256 }` map with a text `path` and a 64-hex `sha256` (`BAD_MATERIAL`), a `repository` that is not a `{ url, commit }` map with a text `url` and a full 40-hex `commit`, either case (`BAD_REPOSITORY`; a value YAML reads as a number is not text), Open Questions missing `owner`, `question_status` or `asked_in` (`QUESTION_NO_FIELD`), an Open Question's `owner` not following the actor convention (`BAD_ACTOR`), `question_status: answered` without `answered_by` (`QUESTION_NO_ANSWER`), `question_status: carried` without `carried_to` (`QUESTION_NO_CARRIED_TO`), `review_on` in the past while `question_status` is `open`, `review_on` that is neither a date nor an ISO 8601 datetime with an offset (`BAD_ISO`), and, in a bundle that has a `base/profile.md`, a key no layer declares (`PROFILE_UNKNOWN_KEY`)). A `distillation_status` outside rule 10 is `BAD_DISTILLATION_STATUS`, and a `question_status` outside rule 13 is `BAD_QUESTION_STATUS`. A validator that fails under `--run-validators` is an error (`PROFILE_VALIDATOR`). A root `okf_version` other than `0.1` or `0.2` is a warning (`UNSUPPORTED_OKF_VERSION`, naming the value and the version inferred instead), never reported as missing. A `profile.md` ignored in a `knowledge/2.0` bundle and a validator not run are notices, like the outdated-profile notice of §9: neither warnings nor errors, and they never fail `--strict`.

**What lint does not judge.** What `.okfignore` matches and a nested bundle (§2) are outside the bundle: no rule applies to them. A **non-OKF directory** is a directory other than the root and its layer directories that has no `index.md` and none of whose Markdown files has a frontmatter with a key of the spec (§3.1: `type`, `title`, `description`, `generated`, `verified`, `sources`, `status`, `tags`, `stale_after`, `resource`, `timestamp` and the other v0.2 keys): a file with no frontmatter, or with only keys such as a site generator's `layout:`. It is not OKF content: rules 1 and 2 do not apply to its files. Inside `fragments/` or `base/` it is one notice, `<directory>/ is not OKF: N Markdown files`. Outside them, in a `knowledge/3.0` bundle, rule 12 still applies, since the root keeps only what is about the bundle as a whole (ADR-0018 decision 3): it is one `PROFILE_OUTSIDE_LAYER` error naming the directory and its number of files, in place of one per file; with `--no-profile`, `knowledge/2.0` or a foreign profile it is the notice. A directory that mixes OKF concepts and plain files is checked file by file, and a plain file in it still breaks rule 1. A file whose frontmatter cannot be parsed counts as OKF, so it keeps its error.

**Rule layers.** Each finding names the rule layer it comes from (`layer` in `--json`), which is neither the bundle's layers (`fragments/`, `base/`, `projections/`, §1) nor the layers of a Domain Profile (built-in, `extends`, `base/profile.md`, named by `source`, §4.1):

| Rule layer | What it checks | Rules |
|---|---|---|
| `spec` | The OKF spec v0.1/v0.2: everything `okf-lint --no-profile` still checks | 1–3, 6 (but `occurred_at` and `review_on`), 7, 8, the form of `generated` and `verified` (`BAD_GENERATED`, `BAD_VERIFIED`, `BAD_ACTOR`), `index.md`/`log.md`, links, `stale_after`, `description`/`title`, versions (`LEGACY_*`, `V02_FIELD_IN_V01`, `MIXED_VERSIONS`, `VERSION_MISMATCH`, `UNSUPPORTED_OKF_VERSION`), `SECRET_IN_BUNDLE` |
| `okf-profile` | The OKF profile itself, `knowledge/3.0` or `knowledge/2.0` | 4, 5 (that `generated` is there: `PROFILE_NO_GENERATED`, `PROFILE_NO_TIMESTAMP` in 0.1), 9, 11, 12, 16, the root `okf_version` (`NO_OKF_VERSION`, `PROFILE_OKF_VERSION`), the audit checks (`FRAGMENT_UNCITED`, `SECTION_EMPTY`, `VERIFIED_STALE`, `FRAGMENT_MATERIAL_CHANGED`, `FRAGMENT_NO_LEDGER`, `LEDGER_GAP`) |
| `domain-profile` | The Domain Profile in force (§4.1), the built-in one included | 10, 13, 14, 15, the Knowledge Fragment and Open Question warnings, `PROFILE_VALIDATOR` |

The summary gives the errors and warnings of each rule layer beside the totals (`spec 0/0 · okf-profile 0/1 · domain-profile 0/0`, errors/warnings), and `--json` gives them under `by_layer`. A root `okf_profile` other than `knowledge/2.0` and `knowledge/3.0` is a **foreign OKF profile**, one okf-builder does not ship: its `spec` checks are reported as usual, and the `okf-profile` and `domain-profile` checks (computed as for a `knowledge/2.0` bundle, the built-in Domain Profile without the bundle's own) are not warnings or errors but one notice naming the profile and how many findings were skipped; `--json` lists them under `skipped` with their codes, and they never fail `--strict`.

**Audit checks.** Lint also reports what it can tell mechanically about the state of the knowledge; what needs judgment is the audit mode of `okf-review`, where a person decides each finding.

| Code | Level | Rule layer | Reported when |
|---|---|---|---|
| `SECRET_IN_BUNDLE` | error | `spec` | A line of a bundle file (frontmatter or body, fragments included; not what `.okfignore` excludes) holds a credential: a JSON Web Token, `Bearer <value>`, `Authorization: <value>`, a known token prefix (`ghp_`, `gho_`, `ghs_`, `github_pat_`, `glpat-`, `AKIA`, `sk-`, `xox[abprs]-`, `AIza`), or a key naming a token, key, password or secret whose value has 16 or more characters, no space, letters and digits, and is not a path, a backtick span, a brace or bracket value or a `{{...}}` placeholder. It names the file and the line in the raw file and never prints the value: lint masks each value it detects in every finding, notice and `--json` field, so no other finding (a `status`, a link target, a path) shows it either. It is a quick check; gitleaks is the thorough scanner, for pre-commit and CI. |
| `FRAGMENT_UNCITED` | warning | `okf-profile` | A Knowledge Fragment with `distillation_status: distilled` that no concept cites: no body link, `sources` entry or Open Question `asked_in` points at it from a file under `base/` (`base/profile.md` included) or from the Conflict Log. Links from `log.md`, an `index.md` or another fragment do not count. A complete ledger (at least one row, and every row's Concept a bundle link that resolves, `tracker` or `no concept (<reason>)`) counts as covered: its rows say where each part went. Type, field and value names are read through the Domain Profile's aliases. |
| `FRAGMENT_NO_LEDGER` | warning | `okf-profile` | A Knowledge Fragment (a local type that extends it included) with `distillation_status: distilled` whose `# Distillation` («Destilado en») holds no ledger: no table of 4 columns, or one with no rows; a table inside a code fence or an HTML comment is not read. There is no date exemption. |
| `LEDGER_GAP` | warning | `okf-profile` | On a distilled fragment, one finding per row of its ledger whose Concept cell (the last of 4, matched by position, the column titles in the bundle's language) is not one or more bundle links, `tracker` (any case, alone) or `no concept (<reason>)` with a non-empty reason without parentheses (an old `—`, an external URL, an empty reason or a mix of forms); and, only when `# Record` («Contenido capturado») has `##` headings, one per heading no row's Item names: an Item names a heading when its text equals the heading's or starts with it followed by a word boundary (ignoring case, emphasis and code marks and trailing punctuation), so `Weekend plans: small talk` names `## Weekend plans` and `Refunds topic` does not name `## Refund`. A bundle link that does not resolve is reported once, as `BROKEN_LINK`, never as `LEDGER_GAP`, and its row does not make the ledger complete. A record without `##` headings is not judged here: whether each paragraph was accounted for is the audit mode of `okf-review`. |
| `SECTION_EMPTY` | warning | `okf-profile` | A concept or reserved file whose type is that of a shipped template (`project.md` uses the Project template; a local type is read as the type it extends) has a `#` or `##` section with a heading of that template whose content, up to the next heading of the same or a higher level, is empty or only placeholder text: a line or list item that is wholly a `{{...}}` placeholder (one inside a backtick span or after `$` is content), an HTML comment, a list item whose text is `...` or ends with `: ...`, or a table row whose cells after the first are all empty or placeholders. Links, table header and separator rows and code are content; a heading inside an HTML comment or a code fence opens no section. |
| `VERIFIED_STALE` | warning | `okf-profile` | A concept whose `generated.at` is later than the `at` of its latest `verified` entry by a `human:` actor: edited after a person verified it; it names both dates. Machine and process verifications are ignored, and so are v0.1 concepts (`timestamp`, no `generated`). |
| `FRAGMENT_MATERIAL_CHANGED` | error | `okf-profile` | A Knowledge Fragment (a local type that extends it included) whose `material` entry, well formed (a text `path`, a 64-hex `sha256`), names a file in the bundle whose SHA-256 is not that `sha256`: the record's source was altered after capture, which breaks its immutability (ADR-0024, ADR-0029). `path` is a bundle path or relative to the bundle root; a file `.okfignore` excludes is still hashed. An absent file, or a path that leaves the bundle (`..`, a symbolic link out of it) or enters a nested bundle, is never read and is a notice, not a finding: material may live outside the repository. Lint never fetches a `repository`. |

`--json` always gives a `metrics` object: `count_per_code` (the findings reported, not the `skipped` ones), `concepts_by_trust` (the concepts under `base/`, neither fragments nor reserved files nor `index.md`, as `unverified`, `machine-confirmed` or `human-reviewed`), `fragments` (`by_status`, each `distillation_status` with its count, and `oldest_pending_days`, the age of the oldest pending fragment from its `occurred_at`, else its `generated.at`, or `null` when there is none), and `stale_after_cluster`, only when at least 4 concepts have `stale_after` and more than a quarter of them fall in one ISO week, listing each such week with its count. The metrics are figures, never findings: they fail nothing.

## 8. Consumption by agents (Claude Code / Cowork)

1. Read `knowledge/index.md` → identify the layers relevant to the question.
2. Read `knowledge/base/index.md` → identify the typed directories relevant to the question.
3. Read the directory's `index.md` → pick concepts by `description`; go to `fragments/` only when the question is about what was said and when. A question about one unit of work (a request, an incident) goes to its bundle, through its kind's directory, and a question about how such work is done stays in the domain bundle's `base/`.
4. Open concepts; follow links only if the question requires it.
5. When answering, cite the concept's path and its trust level (`verified`, `status`, `stale_after`).
6. If the answer uncovers knowledge that is missing or wrong, propose a capture (`okf-capture`) instead of leaving it in the chat.

Recommendation: add a line like this to the repo's `CLAUDE.md`:
`The project's knowledge lives in knowledge/ (OKF format). Start with knowledge/index.md.`

## 9. Supported OKF and profile versions

The profile is **v0.2 by default** and works with **v0.1** for reading, validation, capture and two-way migration. The two breaking changes between versions are `timestamp` → `generated: { by, at }` and `# Citations` (body) → `sources[]` (frontmatter); everything else in v0.2 is additive and optional. A bundle's version is taken from `okf_version` in the root `index.md` and, if missing, inferred from the fields present. Full detail, field matrix and mapping rules in `OKF-COMPATIBILITY.md`.

Operating rules:

- Never mix 0.1 and 0.2 forms in one bundle; `okf-lint` flags it as `MIXED_VERSIONS`.
- When capturing, write in the bundle's version, not the preferred one.
- To exchange with a strict 0.1 consumer, export a downgraded copy (`okf-migrate --to 0.1 --keep-extensions`); the source bundle stays at 0.2.

**Profile versions.** The profile is **`knowledge/3.0` by default**: `okf-init` writes only 3.0 bundles. A bundle's profile is taken from `okf_profile` in the root `index.md`. The older `knowledge/2.0` profile kept the typed directories at the root; `okf-lint` still validates 2.0 bundles by the 2.0 layout and prints a notice that the profile is outdated, which is neither a warning nor an error and never fails `--strict`. The OKF version (0.1 or 0.2) is independent of the profile: migrating the profile does not change `okf_version`, and migrating the OKF version does not change `okf_profile`. Full detail in `OKF-COMPATIBILITY.md`.

Operating rules:

- Migrate a 2.0 bundle with `okf_migrate.py --profile knowledge/3.0`: it moves the typed directories (and any directory the project added) under `base/`, rewrites the bundle-path links and `sources` that point into them (`/decisions/...` → `/base/decisions/...`) and the relative links that cross the layer boundary (from the root files and `fragments/` into the moved directories, and back), sets `okf_profile: "knowledge/3.0"` and logs a **Migration** entry. `--dry-run` is always available.
- Links into a bundle from outside it break when it migrates; update them after the migration.
